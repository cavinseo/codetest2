# 워크시트 자료입력 방식 검토 — 전반 + WS-2·WS-3 집중

**일시:** 2026-08-31 (초판) / **2026-08-31 정정판 rev.2**
**브랜치:** `claude/carp-inspection-46phhc`
**범위:** 워크시트 화면 19개 컴포넌트(약 10,000줄), 저장 라우트 12개, `prisma/schema.prisma` 관계
**방법:** 코드 정독 + 스키마 관계 추적. **실기동 검증은 하지 않았다**(원격 실DB·dev 서버 기동 금지).

> ### ⚠️ rev.2 정정 이력 — 초판의 오류
>
> 초판을 다중 에이전트 반증 검토(조사 7 · 설계 3 · 심사 3 · 반증 4)에 걸었더니 **네 건의
> 주장 중 세 건이 부분·전부 반증됐다.** 초판을 그대로 계획서로 옮기면 **이미 있는 코드를
> 다시 만들게 된다.** 정정 내역은 다음과 같다.
>
> | 초판 주장 | 판정 | 실제 |
> | --- | --- | --- |
> | WS-2 초기화가 DB 를 지우지 않는다 | **확정** | 우회 경로 6개를 모두 확인했고 전부 막혀 있다 |
> | WS-5(고객요구사항)도 전체 교체 저장이다 | **반증** | 이미 id 보존 행 단위 upsert 다 (`requirements/route.ts:80-147`) |
> | WS-3 은 저장할 때마다 id 가 새로 발급된다 | **반증** | id 는 이미 보존된다 (`bulk-save-schemas.ts:86-88`, `attributes/route.ts:96`) |
> | WS-3 저장 시 WS-4 가 "항상" 사라진다 | **부분 반증** | 409 가 `deleteMany` 앞에서 막는다. 손실은 `confirmCascade:true` 를 눌러야 일어난다 |
> | 미저장 이탈 경고를 전 워크시트에 | **범위 축소** | WS-7·WS-9 는 즉시 저장이라 오탐이 난다 |
> | 낙관적 잠금이 전무하다 | **범위 축소** | WS-9 QFD 는 이미 셀 단위 upsert 다 |
>
> 본문은 아래에서 정정했다. 근본 원인의 **표현**이 틀렸을 뿐 **문제 자체는 실재**한다 —
> 다만 원인은 "id 가 새로 발급되어서"가 아니라 **"보존할 행까지 `deleteMany` 로 먼저
> 지워서"** 다. 같은 id 로 다시 만들어도 이미 캐스케이드로 지워진 자식은 돌아오지 않는다.

## 결론

**개선이 필요하다.** 다만 "입력 UI를 예쁘게" 하는 문제가 아니라 **저장 모델**이 원인이다.

대부분의 워크시트가 `deleteMany` + `createMany` 로 **전체를 지우고 다시 만드는** 방식으로
저장한다. 이 하나에서 아래가 전부 파생된다.

- **보존할 행까지 먼저 지운다** → FK 로 물린 하위 워크시트가 cascade 로 사라진다.
  같은 id 로 다시 만들어도 자식은 돌아오지 않는다
- 한 셀만 고쳐도 전체를 보내고 전체를 다시 만든다
- 동시에 편집하면 나중에 저장한 사람이 앞사람 작업을 **통째로** 덮어쓴다

**이 문제는 이미 한 번 풀렸다.** WS-5(고객요구사항)가 `requirements/route.ts:80-147` 에서
행 단위 upsert 로 전환돼 있다. 남은 것은 그 패턴을 WS-3 에 옮기는 일이지, 새로 설계하는
일이 아니다.

그 위에 **미저장 이탈 경고가 저장소 전체에 0건**이라, 사용자가 애써 채운 표가 조용히 사라지는
경로가 둘(이탈, 하위 워크시트 cascade) 열려 있다.

## 1. 전 워크시트 공통

### 1-1. 저장은 대부분 "전체 교체"다 — 한 곳만 예외다

| 라우트 | 방식 | 하위 FK |
| --- | --- | --- |
| sales · dev-plan · tech-roadmap · tech-tree · target-spec | `createBulkWorksheetRoute` 팩토리 (deleteMany + createMany) | 없음 |
| improvements · assets · funding | deleteMany + createMany | 없음 |
| spec (WS-2) | deleteMany + `create` 루프 | 없음(`parentId` 는 일반 컬럼) |
| **attributes (WS-3)** | **deleteMany + createMany** | **AttributeFitness (WS-4)** ← 문제 |
| **requirements (WS-5)** | **✅ 행 단위 upsert (id 보존)** | KanoResponse·QFDMatrix·Benchmark |

팩토리 파일 첫 줄이 이미 그렇게 밝히고 있다 — `// 워크시트 "전체 교체 저장" 라우트를 만드는 팩토리.`

**핵심은 마지막 두 줄이다.** 하위 FK 가 물려 있는 상위 워크시트는 WS-3 과 WS-5 **둘뿐**이고,
그중 WS-5 는 이미 고쳐져 있다. FK 가 없는 leaf 워크시트(팩토리 5개 + improvements·assets·
funding)는 전체 교체로도 잃을 자식이 없어 **지금 방식이 옳다** — 오히려 그쪽 테스트는
`'클라이언트가 보낸 id 는 저장되지 않는다'`(`tests/api-bulk-save-guards.test.ts:106,190`)로
id 유입을 막는 것을 단언하고 있다. 이 단언은 **건드리면 안 된다.**

### 1-2. 그래서 하위 워크시트가 함께 지워진다

스키마의 FK 는 전부 `onDelete: Cascade` 다.

```
ProductAttribute (WS-3)      ←  AttributeFitness (WS-4)
CustomerRequirement (WS-5)   ←  KanoResponse (WS-6·7), QFDMatrix (WS-9), Benchmark
TechnicalCharacteristic      ←  QFDMatrix (WS-9), TechCorrelation
```

상위 워크시트를 **저장하기만 해도** 그 행들이 삭제·재생성되므로 하위 데이터가 cascade 로
사라진다. 지금의 대응은 손실을 피하는 것이 아니라 **손실에 동의를 받는 것**이다 —
`countCascadeImpact`/`countAttributeCascadeImpact` 가 건수를 세고 409 로 확인을 요구한다.

**그 두 가드의 정밀도가 다르다.**

| | WS-5 `countCascadeImpact` | WS-3 `countAttributeCascadeImpact` |
| --- | --- | --- |
| 세는 대상 | **실제로 지워질 기존 행**(`id: { notIn: 제출id }`) | 프로젝트의 **모든** 적합도 |
| 정상 편집(id 유지) | 통과 — 확인 안 물음 | **항상 409** — 매번 확인을 물음 |
| 코드 | `requirements/route.ts:84-111` | `import-cascade-guard.ts:83-89` |

WS-3 가드는 제출 id 를 아예 보지 않으므로(`lib/import-cascade-guard.ts:87` 은 인자로
`projectId` 만 받는다), **오타 한 글자를 고쳐 저장해도 "적합도 N건이 함께 삭제됩니다"가
뜬다.** 늘 뜨는 경고는 읽히지 않는다 — 사용자는 확인을 습관적으로 누르게 되고, 그 순간
`deleteMany` 가 돌아 실제로 WS-4 가 사라진다. **가드가 오히려 손실을 훈련시키고 있다.**

### 1-2-A. TechnicalCharacteristic 은 해당 없음

위 표의 셋째 줄은 상속된 위험이 아니다. 기술특성은 `qfd/technical/route.ts:87` 이
**한 행씩 POST** 로 추가하는 구조라 전체 교체 저장 경로가 없다. 이번 개선 범위에서 뺀다.

### 1-3. 미저장 이탈 경고가 없다

```
$ grep -rn "beforeunload\|beforeUnload" app/ components/ | wc -l
0
```

**대부분의** 워크시트가 입력을 로컬 state 에만 담고 **명시적 "저장" 클릭에만** 영속화한다.
탭을 닫거나, 뒤로 가거나, 다른 워크시트로 이동하면 그때까지 입력한 것이 전부 사라지고
아무 경고도 없다. 워크시트 17개를 순서대로 채워 나가는 제품에서 이 경로는 자주 밟힌다.

**단, "모든"은 아니다 — 경고를 일괄로 걸면 오탐이 난다.**

| 워크시트 | 저장 시점 | 이탈 경고 |
| --- | --- | --- |
| WS-2·3·5 및 팩토리 계열 **12개** | 저장 버튼 | **필요** |
| WS-7 Kano 가중치 | `onBlur` 즉시 저장 (`KanoAggregationTable.tsx:157`) | 불필요 — 걸면 오탐 |
| WS-9 QFD 관계 셀 | 클릭 즉시 POST (`QFDMatrix.tsx:276`) | 불필요 — 걸면 오탐 |

또 하나 — **워크시트 간 이동은 라우터 이동이 아니다.** 탭 전환은 `setActiveTab` 로 컴포넌트를
언마운트할 뿐이라 `beforeunload` 도 Next 라우터 가로채기도 걸리지 않는다. 이 경로를 막으려면
탭 컨테이너가 dirty 상태를 알아야 하므로, 훅 하나를 붙이는 것으로 끝나지 않는다.

### 1-4. 붙여넣기 입력이 없다

```
$ grep -rn "onPaste" app/ components/ | wc -l
0
```

엑셀에서 표 영역을 복사해 붙여넣는, 이런 도구에서 가장 자연스러운 입력 경로가 없다.
대신 **파일 업로드**가 대안인데 3개 워크시트에만 있다(WS-2·WS-3·WS-5). 나머지 10개는
행을 하나씩 추가하며 셀마다 타이핑하는 수밖에 없다.

### 1-5. 키보드 이동이 사실상 없다

`onKeyDown` 이 있는 곳은 `RequirementsTable`(6건)과 `QFDMatrix`(2건)뿐이다. 나머지
워크시트에서는 Tab/Enter 로 다음 셀·다음 행으로 넘어가는 표 입력의 기본 동작이 없어,
셀마다 마우스로 클릭해야 한다.

**다만 이것은 훅 하나로 끝나는 일이 아니다**(초판의 "1~2일"은 과소평가였다). 표마다 열
구성·병합·`datalist`·읽기전용 셀이 달라 셀 좌표계를 컴포넌트별로 세워야 하고, 병합된
셀에서의 이동 규칙은 표마다 다르게 정의해야 한다. 실제 규모는 **6~9일**로 본다.

### 1-6. 클라이언트 검증이 없다

`required`·자릿수·숫자 형식 검증이 어느 컴포넌트에도 없다. 서버 zod 스키마는 일부 있지만,
사용자는 **저장을 누른 뒤에야** 무엇이 잘못됐는지 알게 되고 그 메시지도 행을 짚어 주지 않는다
(`'유효하지 않은 제품 속성 데이터입니다.'`).

### 1-7. 입력 수단이 워크시트마다 다르다

| 수단 | 있는 워크시트 |
| --- | --- |
| 엑셀 업로드 | WS-2, WS-3, WS-5 (13개 중 3개) |
| AI 초안 | WS-2(내장 위저드), WS-3(별도 `AttributeMentorWizard`), WS-16 |
| datalist 자동완성 | 대부분 |
| 초기화 | WS-2, WS-3 |

같은 제품 안에서 워크시트마다 쓸 수 있는 수단이 달라, 사용자가 화면마다 다시 배워야 한다.

## 2. WS-2 (AS-IS 스펙표) — 개별

### ★ WS-2-1. 초기화 버튼이 DB 를 지우지 않는다 (실질 결함)

`SpecTable.tsx:722` 의 `handleReset` 은 빈 배열을 POST 한다.

```ts
body: JSON.stringify({ specFunctions: [] }),
```

그런데 `app/api/projects/[id]/spec/route.ts:78` 이 **조기 반환**한다.

```ts
if (newSpecs.length === 0) {
    return NextResponse.json({
        specFunctions: [],
        message: '스펙이 저장되었습니다',
    });
}
```

`deleteMany` 는 실행되지 않는다. 클라이언트는 200 을 받고 `setRows([])` 뒤
`'AS-IS 스펙표가 초기화되었습니다.'` 토스트를 띄운다.

**결과 — 화면만 비고 DB 는 그대로다. 새로고침하면 전부 되살아난다.** 사용자는 지웠다고 믿는다.

같은 이유로 **행을 전부 지우고 저장해도 지워지지 않는다.** spec 라우트에는 `DELETE` 핸들러도
없어(`GET`·`POST` 뿐) 우회 경로도 없다.

### WS-2-2. 저장 라우트만 zod 검증이 없다

다른 워크시트는 `bulk-save-schemas.ts` 나 `attributesBodySchema` 를 거치는데, spec 만
원본 본문을 그대로 쓴다.

```ts
const newSpecs: Array<{...}> = body.specFunctions || [];
```

저장 필드를 명시적으로 만들어 mass-assignment 는 막히지만, `name` 의 타입·길이나 `order` 의
범위는 아무도 보지 않는다. 행수 상한도 없다.

### WS-2-3. 행마다 개별 INSERT

3단계(CORE→SUB→DETAIL) 루프에서 `tx.specFunction.create()` 를 행 수만큼 호출한다. 팩토리
라우트들은 `createMany` 한 번으로 끝낸다. 계층 id 재매핑 때문에 단계는 나눠야 하지만,
**단계 안에서는 `createMany` 로 묶을 수 있다.** 스펙 트리가 커질수록 트랜잭션이 길어진다.

## 3. WS-3 (제품속성서) — 개별

### ★ WS-3-1. 보존할 행까지 지워서 WS-4 적합도가 사라진다 (구조적 결함) — rev.2 정정

라우트 주석이 이 사실을 그대로 적고 있다(`attributes/route.ts:74-77`).

> 저장은 항상 deleteMany 로 기존 속성을 전부 지우고 다시 만든다. 그 삭제의 캐스케이드로
> 적합도가 함께 사라지므로 …

**초판이 원인을 잘못 짚었다. id 는 이미 보존된다.** 확인한 경로는 셋이다.

| 단계 | 코드 | 상태 |
| --- | --- | --- |
| 화면 → 서버 | `ProductAttributesTable.tsx:339` `rows.map(r => ({...r, ...}))` | ✅ `id` 를 실어 보낸다 |
| 스키마 | `bulk-save-schemas.ts:86-88` — 주석까지 있다: *"`id` is preserved because attribute fitnesses reference it"* | ✅ 통과시킨다 |
| 서버 → DB | `attributes/route.ts:96` `data: newAttributes.map(attr => ({...attr, projectId}))` | ✅ 같은 id 로 다시 만든다 |

**그런데도 WS-4 는 사라진다.** id 를 되살려도 소용이 없기 때문이다 —
`deleteMany`(`:90`)가 먼저 돌면서 캐스케이드로 `AttributeFitness` 행 자체를 지우고, 그
뒤에 `createMany` 가 같은 id 의 부모를 되살려도 **지워진 자식은 돌아오지 않는다.**

> 원인은 "id 가 바뀌어서"가 아니라 **"보존할 행까지 먼저 지워서"** 다.
> 고칠 곳은 스키마도 화면도 아니고 `deleteMany` 의 `where` 절 하나다.

**손실 조건도 정정한다.** 409 가드가 `deleteMany` **앞**(`:78`)에서 반환하므로 트랜잭션에
들어가지도 않는다. 즉 **손실은 사용자가 `confirmCascade: true` 를 눌러야 일어난다.**
초판의 "항상 사라진다"는 틀렸다.

**다만 실질 결과는 거의 같다.** §1-2 에서 본 대로 이 가드는 제출 id 를 보지 않아 **정상
편집에도 매번 뜬다**(`ProductAttributesTable.tsx:352` 가 `window.confirm` 으로 되묻는다).
매번 뜨는 경고는 읽히지 않고, 사용자는 습관적으로 확인을 누른다. 그 순간 손실이 일어난다.

**따라서 결함은 두 겹이다.**

1. `deleteMany` 가 보존할 행까지 지운다 → 원인
2. 가드가 제출 id 를 보지 않아 정상 편집에도 오탐한다 → 사용자를 손실로 훈련시킨다

1번을 고치면 정상 편집에서 지워질 행이 0건이 되므로 **2번도 자동으로 조용해진다.**
WS-5 가 이미 정확히 그 형태다(`requirements/route.ts:84-111`).

### WS-3-2. 셀 병합이 "연속된 동일 문자열"로만 결정된다

`getMarketSegmentSpan` 등이 **인접 행의 문자열 일치**로 rowSpan 을 계산한다.

```ts
if (index > 0 && rows[index - 1].marketSegment.trim() === segment) return 0;
```

그래서

- 오타 한 글자면 병합이 **조용히** 깨진다
- 행 순서를 바꾸면 병합이 깨진다
- 떨어져 있는 같은 값은 병합되지 않는다

이 제약이 AI 프롬프트에까지 새어 나가 사용자에게 전가된다 — `lib/ai/prompts.ts`:

> 같은 세분시장 안에서 고객 니즈와 제공혜택이 동일하면 **같은 문장을 그대로 반복해 넣으세요**

병합은 표현이지 데이터가 아닌데, 데이터를 표현에 맞춰 넣게 하고 있다.

### WS-3-3. WS-2 에서 가져온 값이 복사본이다

`buildSpecPickerRows` 가 WS-2 의 스펙을 골라 **텍스트를 복사**해 넣는다(`pickValue`·`pickTech`).
FK 가 아니라 문자열이므로, WS-2 를 나중에 고쳐도 WS-3 는 옛 문자열을 그대로 들고 있고
둘이 어긋난 것을 알려주는 장치가 없다.

### WS-3-4. 그 함수가 지금 CRAP 최고값이다

`lib/product-attributes-utils.ts:88 buildSpecPickerRows` — 복잡도 16, 커버리지 63%,
**CRAP 29.5**. 방금 끝낸 점검에서 30 에 가장 근접한 함수이며, 위 3번 동작의 본체다.

**게이트 여유가 0.5 밖에 없다.** `.github/workflows/crap.yml` 이 `--fail-over=30` 으로
PR 을 세우므로, 이 함수에 분기를 하나라도 더하면 커버리지를 함께 올리지 않는 한 CI 가
빨개진다. WS-3 를 건드리는 Task 는 이 제약을 미리 알고 들어가야 한다.

### ★ WS-3-5. 스펙 선택기 행병합이 열을 통째로 삼킨다 (rev.2 신규)

`ProductAttributesTable.tsx:72-80` 의 `getRowSpan` — 숨김 판정에 core 비교가 빠졌다.

```ts
const getRowSpan = (arr: FlatRow[], key: 'core' | 'sub', index: number): number => {
    if (index > 0 && arr[index][key] === arr[index - 1][key]) return 0;   // ← core 비교 없음
    let count = 1;
    for (let i = index + 1; i < arr.length; i++) {
        if (arr[i][key] === arr[index][key] && (key === 'core' || arr[i].core === arr[index].core)) count++;
        //                                      ↑ 세는 쪽에는 core 비교가 있다
        else break;
    }
    return count;
};
```

**세는 쪽과 숨기는 쪽의 기준이 다르다.** core 가 다른데 sub 이름이 같은 인접 두 행에서

- 위 행의 `count` 는 core 경계에서 멈춰 `1`
- 아래 행은 `0` 을 받아 `<td>` 가 렌더되지 않는다

결과적으로 **그 행의 세부기능 칸이 사라지고 오른쪽 열이 한 칸씩 밀린다.** "설치"·"관리"
같은 흔한 세부기능 이름이면 바로 재현된다. 값싸고 국소적인 수정이다.

## 4. 개선 제안

비용 대비 효과 순이다. 각 항목은 독립적으로 진행할 수 있다.
**크기는 rev.2 에서 재산정했다** — 초판의 3번·5번은 각각 과대·과소평가였다.

| # | 항목 | 성격 | 초판 | **rev.2** |
| --- | --- | --- | --- | --- |
| 1 | WS-2 초기화 결함 수정 **+ zod 검증** | 버그 | 반나절 | **반나절~1일**(둘을 함께) |
| 2 | WS-3 를 WS-5 패턴으로 전환 | 구조 | (3번에 포함, 3~5일) | **반나절~1일** |
| 3 | WS-3 스펙 선택기 병합 버그 | 버그 | (없었음) | **0.5일** |
| 4 | 미저장 이탈 경고 (저장 버튼 계열 12개) | 손실 방지 | 1~2일 | **1~2일**(범위 축소) |
| 5 | 붙여넣기 입력 | 생산성 | 2~3일 | **2~3일**(WS-5 한정) |
| 6 | 키보드 셀 이동 | 생산성 | 1~2일 | **6~9일** |
| 7 | WS-3 병합을 명시적 그룹으로 | 설계 | 별도 검토 | 별도 검토 |
| 8 | 낙관적 잠금 (종합검진 H-5) | 동시성 | 별도 계획 | 별도 계획(범위 축소) |

### 1. WS-2 초기화 결함 수정 — 먼저, 그리고 zod 와 **반드시 함께**

조기 반환을 걷어내 빈 배열도 실제로 지우게 한다.

**혼자 하면 안 된다.** spec 라우트는 저장소에서 유일하게 zod 검증이 없다(`body.specFunctions
|| []`, `:75`). 조기 반환만 걷어내면 **오타 한 글자짜리 잘못된 본문이 빈 배열로 떨어져
무조건 `deleteMany` 를 돌린다** — 지금보다 나쁜 결함이 된다. 이 사고는 이 저장소에서
이미 한 번 났고, `improvements/route.ts:46-47` 에 그 흔적이 주석으로 남아 있다.

같은 이유로 다른 워크시트 라우트에는 전부 zod 가 붙어 있다. spec 만 예외다.

### 2. WS-3 를 WS-5 패턴으로 전환 — 새로 설계하지 않는다

`requirements/route.ts:80-147` 이 이미 정답 구현이다. **그 구조를 옮긴다.**

```
submittedIds = 제출 행 중 id 가 있는 것
deleteMany({ where: id: { notIn: submittedIds } })   ← 빠진 행만 지운다
for (행) { updateMany 시도 → count===0 이면 create }
```

- 보존할 행을 지우지 않으므로 **WS-4 적합도가 살아남는다**
- `countAttributeCascadeImpact` 를 제출 id 기준으로 바꾸면 **정상 편집에서 409 가 사라진다**
  → 경고가 진짜 위험할 때만 뜨게 되어 다시 읽히기 시작한다
- 낙관적 잠금(8번)을 얹을 자리도 여기서 생긴다

**초판의 "WS-5 에도 적용하면" 은 취소한다** — WS-5 는 이미 되어 있다.
**leaf 워크시트(팩토리 5개 + improvements·assets·funding)로 넓히지도 않는다** — 잃을
자식이 없고, `tests/api-bulk-save-guards.test.ts` 가 오히려 id 유입 차단을 단언한다.

**주의:** 삭제 경로를 건드리므로 실DB 데이터가 걸려 있다. 감리자 확인이 필요하고,
실기동 검증은 실행 AI 에게 위임하지 않는다.

### 3. WS-3 스펙 선택기 병합 버그 — 값싸다

§3 WS-3-5 의 `getRowSpan`. 숨김 판정에 `arr[i].core === arr[index].core` 를 더하면 끝이다.
다만 `buildSpecPickerRows` 가 CRAP 29.5 라 게이트 여유가 0.5 뿐이므로, 분기를 더한
만큼 테스트로 덮어야 한다.

### 4. 미저장 이탈 경고 — 범위를 좁혀서

dirty 플래그 + `beforeunload` + Next 라우터 이동 가로채기. **§1-3 의 12개(저장 버튼 계열)
에만** 건다. WS-7·WS-9 는 즉시 저장이라 제외한다.

**탭 전환은 이 훅으로 못 막는다**(언마운트이지 라우터 이동이 아니다). 1차 범위에서 빼고,
필요하면 탭 컨테이너에 dirty 상태를 올리는 별도 작업으로 다룬다.

### 5. 붙여넣기 입력

`onPaste` 에서 클립보드 TSV 를 파싱해 여러 행·열을 한 번에 채운다. 엑셀 업로드보다 훨씬
자주 쓰이는 경로이고 파일 왕복이 없다. 업로드 파서(`lib/excel-parser.ts`)의 정규화 규칙을
그대로 재사용할 수 있다. **2~3일은 워크시트 하나(WS-5) 기준이다** — 표마다 열 구성이
달라 전 워크시트로 넓히면 배수로 늘어난다.

### 6. 키보드 셀 이동 — 6~9일

Tab/Shift+Tab/Enter/방향키로 셀 이동, 마지막 셀에서 Enter 로 새 행. §1-5 에 적은 대로
표마다 좌표계와 병합 규칙이 달라 공통 훅 하나로 끝나지 않는다.

### 7. WS-3 병합을 명시적 그룹으로 — 설계 판단 필요

문자열 일치 대신 그룹 식별자를 두는 방식이 정공법이지만 스키마와 화면이 함께 바뀐다.
그 전에 값싼 완화책도 있다 — **인접하지 않은 동일 값**이나 **한 글자 차이로 갈라진 값**을
경고로 띄우는 것만으로 "조용히 깨지는" 문제의 대부분은 드러난다.

### 8. 낙관적 잠금 — 종합검진 H-5

2026-08-20 종합검진이 "18개 라우트 + 스키마 변경이라 의도적 제외"로 남긴 항목이다.
확인 결과 지금도 낙관적 잠금 흔적이 없다.

```
$ grep -rniE "optimistic|updatedAt.*where|version.*conflict" app/api/projects/ lib/bulk-worksheet-route.ts
(없음)
```

전체 교체 저장이 유지되는 한 동시 편집은 **항상** 덮어쓰기다. 2번을 먼저 하면 이 작업의
범위가 줄어든다.

**범위 축소(rev.2):** WS-9 QFD 관계는 이미 셀 단위 upsert 라(`QFDMatrix.tsx:276`)
덮어쓰기 폭이 셀 하나다. "18개 라우트"는 실제보다 큰 숫자다.

## 5. 이 검토에서 하지 않은 것

- **실기동 검증을 하지 않았다.** WS-2 초기화 결함은 코드 경로로 확정했으나 화면에서
  재현하지는 않았다(dev 서버 기동 금지). 조치 전에 감리자 또는 사용자가 실계정으로
  한 번 재현해 두면 좋다.
- **사용자 조사를 하지 않았다.** 우선순위는 코드에서 읽은 위험도 기준이다. 실제 사용자가
  어느 워크시트에서 가장 오래 머무는지는 다른 근거가 필요하다.
- **WS-6~WS-17 을 개별로 파고들지 않았다.** 요청 범위가 전반 + WS-2·WS-3 이었고,
  나머지는 §1 의 공통 항목으로 묶어 다뤘다.
