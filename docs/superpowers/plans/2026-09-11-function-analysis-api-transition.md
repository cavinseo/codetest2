# 기능분석 도우미의 향후 API 전환 설계.

## 현재 상태와 이번 결정.

상태는 **전환 구조 검토·기록 완료, API 기능 미구현·미활성화**이다. 2026-09-11 사용자는 당분간 현재 프롬프트 제공 방식을 사용하고, 향후 전환에 영향을 줄 구조만 미리 검토하도록 요청했다.

- 현재 질문 → 프롬프트 생성 → 복사 흐름을 유지한다. 프롬프트 제공에 5회 제한을 적용하지 않는다.
- 정식 버전에서는 도우미가 기존 WS-2 ‘AI 에이전트’를 대체하고, 프롬프트를 API로 직접 실행할 계획이다.
- 향후 멘티의 실행 한도는 **멘티 계정 전체 누적 5회**다. 프로젝트별·프로그램별·기간별 한도가 아니다.
- 프로젝트 추가·이동·삭제, 소유권 이전, 프로그램 변경·기간 연장, 재로그인으로 같은 계정의 누적 사용량을 초기화하지 않는다.
- 결과 형식은 현행 FAST-WS2-1.2의 HTML 보고서와 마지막 WS-2 엑셀 붙여넣기용 4열 표를 유지한다.
- 이번에는 API 라우트, 사용량 테이블, 실행 버튼, 환경변수·전환 스위치, 신규 패키지나 사용량 수집을 추가하지 않는다. 기존 AI 에이전트도 지금 제거하지 않는다.

## 소스 검토 결과.

| 확인한 코드 | 사실과 전환 시 주의점 |
| --- | --- |
| `lib/function-analysis-prompt.ts` | imports 없는 순수 함수이며 입력 타입·검증·프롬프트 버전이 이미 분리되어 있다. 현재 구조를 서버와 브라우저의 공통 생성기로 유지하면 된다. |
| `components/project/FunctionAnalysisAssistant.tsx` | UI 상태와 복사를 담당하고 순수 생성기를 호출한다. 현재는 서버 실행·DB 저장이 없다. UI에 공급자 호출이나 차감 로직을 넣지 않는다. |
| `components/project/SpecTable.tsx` | 프로젝트별 도우미 생명주기와 기존 쓰기 권한을 적용한다. 현재 표 반영 콜백을 도우미에 넘기지 않는다. |

| `lib/ai/registry.ts` | 공급자 실패 시 규칙 엔진으로 대체한다. HTTP 200이나 `degraded=false`만으로 실제 API 분석 성공을 판정할 수 없다. |
| `app/api/projects/[id]/spec/generate/route.ts` | 기존 AI 실행은 개인 연결 및 규칙 엔진을 선택하고 경우에 따라 브라우저 로컬 중계를 제안한다. 도우미 전환 시 별도 실행 정책이 필요하다. |
| `app/api/projects/[id]/spec/generate/complete/route.ts` | 브라우저가 보낸 결과를 받는 무상태 경로다. 서버가 발행한 실행 이력이 없으므로 누적 한도의 실행·차감 근거로 재사용하지 않는다. |
| `lib/auth.ts`, `lib/authorization.ts`, `prisma/schema.prisma` | 인증 후 확인한 `User.id`가 계정 기준이다. `User.programId`, 프로젝트 소유자, 이메일, 초대코드는 사용량 소유 키로 쓰지 않는다. |
| `app/api/admin/users/route.ts` | 멘티 계정을 실제 삭제할 수 있다. 삭제 후 재가입자의 한도 승계 여부는 아래 미확정 정책으로 남긴다. |

지금 필요한 준비는 이 경계와 전환 검수 기준의 기록이다. 재사용을 위한 입력 DTO·서비스 계층·전략 인터페이스를 미리 추가하지 않는다. 외부 API를 연결할 실제 작업에서 필요한 최소 타입과 구현을 추가한다.

## 전환할 때 지켜야 할 설계 기준.

### 1. 프롬프트 생성과 API 실행을 분리한다.

- 현행 `buildFunctionAnalysisPrompt`를 단일 생성기로 재사용한다. 공급자·인증·사용횟수·저장·시간·무작위 상태를 이 함수에 넣지 않는다. 현재 프롬프트 제공 기능은 API 연결 상태와 관계없이 동작해야 한다.
- 향후 서버는 인증된 사용자와 프로젝트 접근권한을 검사한 뒤, 질문 답변 및 현재 WS-2 포함 여부를 검증하고 공통 생성기로 프롬프트를 다시 만든다. 클라이언트가 보낸 사용자 ID·잔여 횟수·최종 프롬프트를 실행 권한이나 차감 근거로 신뢰하지 않는다.
- 기존 답변 검증은 TypeScript 입력에 대한 로컬 검증이다. API 도입 시 JSON 구조·문자열 타입·필수값·전체 크기·기존 표 행 수를 서버 경계에서 검증한다. API가 없는 지금 별도 요청 스키마를 추가하지 않는다.
- WS-2 포함을 선택한 경우 서버가 해당 프로젝트 자료를 읽고 실행 시점의 입력을 고정한다. 포함 해제 시에는 실제 요청에도 제외한다. 화면의 미저장 표를 실행에 반영할지는 전환 전에 결정한다.
- 실행 기록에는 실제 사용한 프롬프트 버전, 입력 식별값, 공급자·모델과 결과를 함께 연결한다. 배포 후 재조회·재시도 시 바뀐 프롬프트로 조용히 다시 실행하지 않는다.
- HTML 분석 결과는 기존 JSON 기능 트리 및 멘토가 완료하는 결과보고서와 목적·권한·생명주기가 다르다. 기존 `specDraft`나 `final_reports`에 무리하게 끼워 넣지 않는다.

### 2. 사용량은 계정에 귀속하고 서버에서 원자적으로 관리한다.

- 차감 대상은 인증된 실행 요청자의 멘티 `User.id`다. 해당 요청자가 사용할 수 있는 프로젝트인지는 별도로 검사한다. 멘토·매니저·관리자의 대리 실행과 한도 정책은 아직 확정하지 않는다.
- 계정의 누적 사용량과 요청별 실행 이력을 영속 저장한다. 프로젝트·프로그램 수명에 따라 사용량 이력이 연쇄 삭제되는 관계를 만들지 않는다. 결과 자료의 삭제와 이미 사용한 횟수의 유지가 함께 가능해야 한다.
- 실행 가능 여부 확인과 슬롯 예약을 하나의 DB 트랜잭션에서 처리한다. 단순히 횟수를 읽은 뒤 API를 호출하고 마지막에 +1 하면 병렬 요청이 5회를 넘길 수 있다. ‘확정 사용 + 실행 중 예약 ≤ 5’를 유지한다.
- 외부 모델 응답을 기다리는 동안 DB 트랜잭션을 열어 두지 않는다. 짧은 예약 처리 → 외부 실행 → 결과 보존 및 정책에 따른 확정·해제 순서로 처리한다. Prisma도 긴 트랜잭션 안의 네트워크 요청을 피하도록 안내한다. [Prisma 6 트랜잭션 문서](https://www.prisma.io/docs/orm/v6/prisma-client/queries/transactions).
- 동일 요청의 재전송은 계정별 고유 요청 키로 같은 실행에 연결한다. 다른 입력으로 같은 키를 재사용하면 거부한다. 새로고침·중복 클릭·통신 재시도로 새 실행이나 이중 차감이 생기지 않아야 한다.
- 사용량과 실행 기록의 쓰기는 서버만 수행한다. 향후 Supabase에 테이블을 추가할 때 RLS와 공개 접근 권한도 함께 검증한다. 이 앱의 실제 인증 경계를 따르고 별도 Supabase Auth 사용자 ID가 있다고 가정하지 않는다.

### 3. 공급자 오류와 실행 중단을 구분한다.

- API 분석 성공은 실제 선택된 공급자의 완료 응답과 요구 형식 검증을 기준으로 판단한다. 기존 규칙 엔진의 대체 결과나 브라우저가 제출한 결과를 API 성공으로 세지 않는다.
- 성공 후 결과 저장과 사용량 확정이 어긋나지 않게 한다. 이미 저장된 결과 열람·다운로드·복사는 새로운 분석 실행이 아니다.
- 서버 중단·응답 유실·시간 초과로 원격 실행 결과가 불확실할 수 있다. 이를 확정 실패로 간주해 즉시 슬롯을 돌려주고 자동 재호출하지 않는다. 실행 ID·공급자 요청 식별자와 상태를 남기고, 공급자가 지원할 때만 결과를 재조회한다. 재조회가 불가능하면 원격 결과 불확실 상태를 보존하고 확정된 조정 정책으로 처리한다. 상태 확인 자체는 새 모델 호출을 하지 않는다.
- 사용자 실행 횟수와 실제 공급자 요청·비용은 구분한다. 동일 실행의 내부 재시도 비용, 호출 전 실패, 출력 잘림·형식 불일치, 저장 실패, 취소·불확실 상태의 차감·해제 기준은 구현 전에 확정한다.
- 실제 공급자의 문서, 출력 한도, 응답 시간과 배포 환경 제한은 전환 시 다시 확인한다. 현재의 긴 8절 분석과 최종 표가 잘리지 않는지 검증한 후 동기 처리 또는 비동기 실행 방식을 선택한다. 지금 공급자·모델·작업 큐를 고정하지 않는다.

### 4. HTML 표시와 WS-2 저장을 분리한다.

- ‘JavaScript를 생성하지 말라’는 프롬프트 지시만으로 안전한 HTML이라고 판단하지 않는다. 서버에서 문서 크기·8개 분석 절·마지막 4열 표를 검증하고, 표시 전에 허용한 HTML·CSS·URL만 남기는 정제와 격리를 적용한다.
- 앱 본문에 원문 HTML을 직접 주입하지 않는다. 미리보기는 스크립트·폼·상위 화면 이동 권한을 주지 않는 격리된 표시 영역을 사용하고 외부 리소스 요청도 차단한다. iframe의 sandbox와 네트워크 차단 정책은 별도로 검증한다. [MDN iframe 문서](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/iframe#sandbox).
- 정제 후에도 표의 열·행과 텍스트가 유지되어야 한다. HTML 다운로드, 브라우저에서 복사, Excel 붙여넣기를 실제로 검수한다. 자동 표 반영을 도입할 때도 검토·명시적 저장 단계와 기존 WS-2 쓰기 권한을 유지한다.

### 5. 기존 AI 에이전트의 교체는 서버 경로까지 포함한다.

- 전환 승인 시 UI 버튼만 교체하지 않는다. 기존 `spec/generate`, `spec/generate/complete`, 브라우저 중계 경로가 새 한도를 우회하는 대체 실행 경로로 남지 않도록 호출처와 직접 요청을 함께 점검한다.
- WS-3 등 다른 AI 기능이 공유하는 provider registry와 개인 연결 설정을 일괄 제거하거나 동작을 바꾸지 않는다. 필요한 전송 어댑터·키 보관 코드를 재사용하되 HTML 분석 결과와 성공 판정은 별도 작업 계약으로 둔다.
- 전환 중 운영을 일시 중단하더라도 누적 사용량을 지우지 않는다. 현재 복사 도우미로 복귀할 수 있도록 배포 순서와 데이터 보존을 검증한다.

## 전환 전에 확정할 정책.

다음은 사용자가 아직 확정하지 않은 항목이며 이번 작업에서 임의로 적용하지 않는다.

1. 실패한 실행의 차감 여부. 성공 결과가 확정될 때만 차감하는 방식은 권장안이며 아직 승인된 규칙이 아니다. 출력 잘림·형식 오류·취소·원격 결과 불확실·저장 실패 각각을 결정한다.
2. 멘토·매니저·관리자의 실행 허용 여부와 대리 실행 시 한도 소유자, 예외 추가 부여·초기화 권한.
3. 계정 삭제 후 재가입·계정 통합의 한도 승계. 현재의 확정 범위는 같은 `User.id`의 누적이며, 동일인 추적용 개인정보나 삭제 이력을 지금 신설하지 않는다.
4. 공급자·모델·키 소유자, 비용 예산과 재시도·보관 기간, 미저장 WS-2 입력 처리.
5. 현재 복사 사용이나 과거 AI 사용량은 새 실행 원장의 근거가 아니다. 도입 전 사용을 소급 추정하여 차감하지 않는 것을 전환안으로 두고 적용 시작점을 확정한다.
