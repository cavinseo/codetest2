# 워크시트 개선 실행계획.

## 요청과 확정된 조건.

- 사전 계획 보고 후 사용자가 실행을 승인했다. 현재 소스 구현과 로컬 검증은 완료했으며 실제 서비스 데이터 변경과 배포는 대기 중이다.
- WS-10은 선택한 핵심스펙 안의 세부기술과 세세부기술을 계층으로 표시한다. 사용자가 2026-09-08 추가 답변으로 확정했다.
- WS-12는 스펙분류, 세부항목, 기술적 특성, 개선여부의 4열로 구성한다. WS-2 AS-IS를 먼저 가져온 뒤 WS-11의 신규 기능을 분류하여 추가한다.
- WS-13은 WS-11의 개선포인트 우선순위(고객니즈)를 원본 순서대로 자동 나열한다.
- WS-16은 기존 2·3차년도 매출도 한 번 빈칸으로 초기화한다. 이후 작성자의 입력은 저장한다. 사용자가 2026-09-08 추가 답변으로 확정했다.
- 모든 워크시트의 금액 입력과 표시에는 세 자리 구분 콤마를 적용한다.
- WS-17은 내용이 잘리지 않도록 표의 가로폭을 확보한다.

## 검토 결과와 데이터 보존 원칙.

1. WS-10은 팝업과 자동완성 모두 전체 핵심스펙의 후보를 섞어 표시한다. 현재 후보 생성은 세세부기술이 있으면 상위 세부기술을 생략하며, 입력창 선택과 팝업 선택의 기술특성 반영 동작도 다르다.
2. WS-12는 6열이며, 빈 문서에 WS-2 대신 개선기능 추천을 넣는다. 추천 기술특성은 기능과의 관계가 아니라 배열 순번으로 배정되므로 새 기능의 기술특성으로 사용하면 안 된다.
3. WS-11의 해당 고객니즈는 화면상 `customerNeed`, 저장상 `content`이다. `priority` 필드가 아니다. need/feature를 조합하는 WS-11 표시 규칙과 동일한 순서를 사용해야 한다.
4. WS-11과 WS-13은 저장 시 행을 전체 교체하고 ID를 다시 만든다. 단순 행 번호나 변경되는 ID로 연결하면 순위 변경 때 기존 작성 내용이 다른 니즈에 붙을 수 있다.
5. WS-16은 조회할 때 WS-1 매출을 세 연도에 모두 덮어쓴다. 연도 저장 필드는 숫자 기본값 0이므로 빈칸과 실제 0을 구분하려면 저장 계약도 변경해야 한다.
6. WS-17은 표 카드 하나를 두 열 레이아웃의 왼쪽에만 배치한다. 사용하지 않는 오른쪽 열 제거가 폭 확보의 첫 수정이다.

기존 WS-12·13 작성 내용과 WS-16 비용 및 WS-17 조달액은 보존한다. 사용자에게서 초기화가 확정된 항목은 WS-16의 기존 2·3차년도 매출이다. 초기화 대상 프로젝트와 행을 적용 전에 특정하고, 이후 조회나 재배포 때 반복 초기화되지 않도록 한다.

## 단계별 실행과 완료 기준.

### 1단계. 데이터 매핑과 재현 기준을 고정한다.

- [x] 아래 단계의 경계 사례를 포함하는 모의 데이터를 준비하고 현재 결함을 재현하는 테스트를 작성한다.
- [x] WS-12의 3단계 원본을 4열로 옮기는 매핑을 확정한다. 제안은 핵심기술을 스펙분류에, 세부기술과 세세부기술의 경로를 세부항목에, 각 원본 행의 적용기술을 기술적 특성에 두는 것이다. 명칭, 기술 문구, 순서는 보존한다.
- [x] WS-13의 자동 반영 시점은 WS-11 저장 후 WS-13 진입 또는 재조회로 잡는다. 기존 입력과 같은 고객니즈는 내용을 보존하며 정렬한다. 중복 이름·이름 변경·삭제 때문에 연결이 불명확하면 순번으로 임의 연결하거나 기존 행을 삭제하지 않는다. 지속적인 원본 추적이 필요한 부분의 식별자 보존 방식을 구현 전에 고정한다.
- [x] 기존 WS-16 매출 초기화의 대상과 1회 적용·복구 절차를 문서화한다.

검증 기준은 서로 다른 핵심스펙 아래의 같은 이름, 세세부기술 여러 개, 기술특성 없음, 기존 WS-12·13 수기 내용, 매출 빈칸·0·양수 사례가 모두 준비되는 것이다.

### 2단계. WS-10의 선택과 기술특성 반영을 수정한다.

- [x] `lib/tech-tree-utils.ts`에서 부모 관계와 항목 식별자를 가진 계층 후보를 만든다. 핵심스펙 자신을 하위 후보로 대체하지 않는다.
- [x] `components/project/TechTreeTable.tsx`에서 해당 행의 핵심스펙으로 팝업과 자동완성 후보를 제한한다. 세부기술 아래에 세세부기술을 들여쓰기하여 표시한다.
- [x] 선택 경로를 통일하여 선택한 항목의 기술특성을 같은 행에 자동 반영한다. 다른 핵심스펙이나 관계없는 상위 항목의 기술특성을 임의로 대신 넣지 않는다.
- [x] 핵심스펙 미선택·후보 없음·기술특성 없음 상태를 안내한다. 핵심스펙 변경으로 기존 선택이 유효하지 않아지는 경우 재선택 상태를 명확히 표시한다.

완료 기준은 핵심스펙 A가 선택된 행에서 A의 하위 계층만 보이고, 하위 항목을 선택하면 그 항목의 기술특성이 표시·저장되며, 다른 고객니즈나 핵심스펙 그룹의 값은 바뀌지 않는 것이다.

### 3단계. WS-12를 AS-IS 기반의 4열 작성 흐름으로 바꾼다.

- [x] `app/api/projects/[id]/target-spec/route.ts`와 `lib/worksheet-links.ts`에서 WS-2 원본 행과 WS-11 신규 기능 후보를 구분하여 제공한다. WS-2 기술특성은 배열 순번으로 추정하지 않는다.
- [x] `components/project/TargetSpecTable.tsx`를 요청한 4열로 변경한다. 첫 작성 시 WS-2 AS-IS를 채우고, 저장된 WS-12가 있으면 기존 작성 내용을 먼저 보존한다.
- [x] 신규 기능 추가 화면에서 WS-11의 추가 기능을 선택하고 귀속할 핵심스펙과 세부항목을 지정하여 해당 그룹에 삽입한다. 성능향상 내용은 함께 참고할 수 있게 하되 관계없는 기술특성을 자동 배정하지 않는다.
- [x] 기존 AS-IS 유지와 추가·개선 상태를 개선여부에서 구분한다. 재진입이나 같은 기능 재추가로 중복 행이 생기지 않도록 한다.
- [x] 화면에서 제외되는 측정단위·설계 목표치 등 기존 저장 필드는 저장 과정에서 유실되지 않게 한다. `lib/workbook-importer.ts`의 기존 4열 가져오기와 호환성을 검사한다.

완료 기준은 첫 작성에서 원본의 핵심·세부·세세부 내용과 기술특성이 누락되지 않고, 신규 기능을 원하는 분류와 세부항목에 추가한 결과가 저장·재진입 후 유지되는 것이다.

### 4단계. WS-13에 고객니즈를 순서대로 자동 반영한다.

- [x] `components/project/TechRoadmapTable.tsx`에서 기존 WS-11 조회 API와 WS-13 데이터를 함께 읽는다.
- [x] `lib/worksheet-links.ts`에 WS-11 화면과 동일한 고객니즈 추출·정렬 규칙을 두고, `category`에 고객니즈를, `order`에 원본 순서를 반영한다. 화면의 순위는 1부터 표시한다.
- [x] 빈 템플릿 행은 제외하고, 해당 니즈에 작성된 개선기능·구현가능성·목표 고객을 보존한다. WS-11 조회 실패 시 기존 WS-13 내용을 비우지 않는다.
- [x] 순위 변경·중복 고객니즈·이름 변경에서 기존 입력이 다른 니즈에 붙지 않도록 1단계의 연결 정책을 적용한다. 가져온 기존 목표 고객이 `owner`에 저장된 사례도 보존 검증에 포함한다.

완료 기준은 WS-11에서 저장한 유효 고객니즈가 같은 순서로 자동 표시되고, WS-13의 기존 수기 내용이 저장과 재조회 후에도 올바른 항목에 유지되는 것이다.

### 5단계. WS-16의 매출 입력과 전체 금액 형식을 수정한다.

- [x] `prisma/schema.prisma`와 신규 migration에서 2·3차년도 매출의 빈칸을 표현할 수 있게 한다. 비용행의 기존 기본값은 유지한다.
- [x] `lib/bulk-save-schemas.ts`, `app/api/projects/[id]/funding/route.ts`, `lib/worksheet-links.ts`에서 WS-1 연동을 1차년도에만 적용하고, 2·3차년도는 숫자 또는 빈칸으로 저장한다.
- [ ] 운영 적용 시 기존 2·3차년도 매출을 확정된 적용 대상에 한하여 한 번 비운다. SQL 작성 및 독립 PostgreSQL 검증은 완료했으며 실제 서비스 적용은 대기 중이다. 이 처리를 일반 GET이나 매번 실행되는 초기 로딩 코드에 넣지 않는다.
- [x] `components/project/FundingTable.tsx`에서 2·3차년도 매출을 입력창으로 변경하고, 삭제하면 빈칸으로 저장하며 실제 0은 0으로 유지한다.
- [x] `lib/funding-ai-agent.ts`와 `lib/workbook-importer.ts`에서 빈칸·0·수동값을 보존한다. AI 초안을 사용해도 수동 매출을 채우거나 덮어쓰지 않는다.
- [x] 구조화된 금액을 사용하는 `components/project/SalesTable.tsx`와 `FundingTable.tsx`의 입력·합계·그래프·요약 표시를 점검하여 세 자리 콤마를 통일한다. WS-1의 기존 콤마 동작은 보존한다.
- [x] 화면의 콤마는 저장·계산 전에 제거하며 소수와 숫자 정밀도를 유지한다. WS-17의 JSON 및 기존 문자열 형식도 같은 합계를 내도록 `parseSourceYear`를 검증한다.

완료 기준은 기존 매출 초기화 후 입력한 2·3차년도 값이 WS-1 수정·저장·재조회·AI 실행 이후에도 유지되고, 1,000 및 소수 금액이 화면과 합계에서 일치하는 것이다.

### 6단계. WS-17 표가 가용 폭을 사용하도록 수정한다.

- [x] `components/project/FundingTable.tsx`에서 표 하나에 적용된 불필요한 두 열 분할을 없앤다.
- [x] 표와 구분·출처·금액 열에 충분한 최소폭을 배정한다. 긴 문구에는 줄바꿈 또는 전체 내용 확인 방법을 제공하며 좁은 화면에서는 가로 스크롤을 유지한다.
- [x] 일반 프로젝트 탭과 직접 접근 페이지에서 같은 폭과 입력 동작을 확인한다.

완료 기준은 긴 TIPS/R&D 명칭, 긴 조달처, 큰 콤마 금액을 넣어도 내용을 확인·편집할 수 있고 모든 연도 열에 접근할 수 있는 것이다.

## 실행 순서와 범위.

1단계 이후 WS-10 → WS-12 → WS-13 → WS-16·금액 형식 → WS-17 → 통합 검증 순서로 구현한다. 같은 `worksheet-links.ts`와 `FundingTable.tsx`의 수정은 순차 통합한다. 검토와 테스트 분석은 병렬로 수행할 수 있으나 최종 판정은 주 작업자가 맡는다.

2026-09-08 승인 후 기능 구현과 로컬 통합 검증을 완료했다. 실제 서비스 DB 초기화 및 배포는 수행하지 않았다. 운영 적용 항목을 남겨 상태는 in-review로 유지한다.


## 최종 검증 결과.

- 전체 테스트 110개 파일, 1,265개 통과.
- 타입 검사 성공. 전체 린트 오류 0개이며 기존 Stryker 임시 파일 경고 4개가 있다. 최종 변경 소스·테스트 대상 린트도 성공했다.
- 최종 npm run build 성공. Google Fonts 다운로드에는 네트워크 허용이 필요했다.
- 실제 React 컴포넌트와 모의 API로 브라우저의 선택·저장·재조회·빈칸 삭제·AI 실행·가로 스크롤을 검증했다.
- 로컬 PostgreSQL 16의 독립 DB에서 migration.sql 실행 및 매출행만 초기화, 1차년도·비용 보존, 이후 null·0·소수 저장을 검증했다. 검증용 PostgreSQL 서버는 종료했다.
- 수정 전 소스에서는 실패하고 수정 후에는 통과하는 WS-10 계층·기술특성 및 WS-16 매출 보존 시나리오를 독립 재현했다.

## 검토에서 보완한 사항.

- 금액 포맷 변경 후 커서를 복원하여 앞·중간·소수 연속 편집을 보존했다.
- 동명 스펙은 선택 전 대상 행을 고정하고 부모 경로로 표시·저장하여 인접 행을 덮어쓰거나 다시 병합하지 않는다.

## 운영 적용 시 확인할 사항.

- 대상은 funding_plans에서 category 또는 item이 '매출액'인 기존 행의 year2·year3이며 모든 해당 프로젝트에 적용된다. 다른 금액은 바꾸지 않는다.
- 적용 전 해당 테이블의 백업과 대상 행 수를 확인한다. 실제 운영 DB 조회·백업·적용은 이번 로컬 검증에 포함하지 않았다.
- 마이그레이션 이력을 사용하는 정상 배포 절차로 한 번 적용하고 이어서 새 애플리케이션을 반영한다. SQL 파일을 재실행하면 새 수동값도 초기화하므로 수동 재실행하지 않는다.
- 복구가 필요하면 백업의 행 ID를 기준으로 두 연도값만 복원한다. 운영 적용 전에 백업을 확보해야 한다.
