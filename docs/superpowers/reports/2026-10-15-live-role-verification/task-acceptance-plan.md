## 실제 UX 확인의 우선순위

1. **P1 — 삭제 버튼의 범위를 구분한다.** 응답자 표의 ‘전체 삭제’와 설문 관리의 ‘응답 데이터 리셋’은 초대를 유지한다. 별도 ‘초대 내역 리셋’은 응답과 초대를 모두 삭제한다. 후자를 전체 응답 삭제 검증의 대체 버튼으로 사용하면 초대 보존을 검증할 수 없다. S2:533·543·1249, S3:87이 근거다. 초대 리셋 확인창은 응답자 수로 인원을 표시하므로 미응답 초대까지 포함한 삭제 규모와 숫자가 다를 수 있다.
2. **P1 — 요구사항 연결 삭제 확인은 응답 삭제 확인과 별개다.** 일반 기존 행 편집은 ID를 보존하는 저장이다. 요구사항을 모두 삭제하는 저장 등에서 서버가 연결 응답 영향을 반환하면 별도 native 확인창이 뜬다. 취소하면 추가 확인 저장을 보내지 않고 기존 서버 데이터를 유지해야 한다. 이 연결 삭제는 통상적인 입력 저장 성공 검증에 필요하지 않다. S1:242·245, T4:117·127이 근거다. 기존 UI 테스트에는 이 확인창의 브라우저 조작 근거가 없고 API의 409/확인 계약만 있다.
3. **P2 — 성공 알림과 화면 값만으로 영속 저장을 판정하지 않는다.** WS-5의 행 ‘편집 반영’은 메모리 편집 확정이고 상단 ‘저장’이 실제 저장이다. Kano는 재조회 때 사용자가 편집한 질문을 보존하므로 같은 화면의 수정값 유지 자체가 서버 저장 증거는 아니다. 두 역할 모두 새로고침한 결과를 기록한다. S1:209·641, S2:194·552가 근거다.
4. **P2 — native 확인창을 실제로 관찰한다.** 확인창 문구는 DOM 내 모달이 아니다. 기존 테스트는 `window.confirm`의 반환값을 모의한다. 실제 브라우저에서 창이 뜨는지, 인원과 안내가 읽히는지, 취소와 확인이 각각 동작하는지는 별도 운영 관찰이 필요하다. S3:39, T2:51·105가 근거다.
5. **P2 — 삭제 성공 뒤 로딩을 빈 상태와 구분한다.** 삭제 후 `loadData()`가 목록·초대·집계와 허용된 상세 분석을 다시 읽는다. 로딩 종료 뒤 결과와 새로고침을 확인한다. 재조회 오류로 응답자 진입점이 없어지는 상태를 정상 빈 응답 목록으로 판정하지 않는다. S2:162·522·627, T2:259가 근거다.

위 항목은 소스에서 확인한 범위 차이와 관찰상 주의사항이다. 운영에서 발생한 결함을 발견했다는 의미는 아니다.

## 읽기 전용 판정과 미검증 한계

읽기 전용 검토로 확인한 것은 저장·확인·삭제·재조회 경로, 역할별 기대 접근, 테스트의 단언 범위다. 기존 테스트는 fetch·DB·권한·confirm 등을 모의하므로 실계정 인증, 실제 배정·소유 관계, 운영 데이터 반영, native 창 표시, 네트워크와 배포 환경의 동작을 증명하지 않는다. 이 검토에서는 테스트를 실행하지 않았다.

루트의 전달 내용에 따르면 운영 로그인 화면을 열었으나 로그인 세션과 검증 프로젝트는 아직 지정되지 않았다. 실제 운영 입력 저장·응답 삭제·확인창 조작 검증은 미수행이며 모든 표의 운영 성공 여부는 미검증이다. 실제 운영 확인은 루트의 브라우저 조작 결과로만 판정한다. 로그인 세션이나 필요한 응답 데이터가 없거나 native 창 조작을 확인하지 못하면 해당 시나리오를 미검증으로 표시하고 사유를 기록한다. 운영 완료 보고에는 계정 역할별 프로젝트 식별값, 시나리오별 결과, 전후 관찰 근거와 남은 미검증 항목이 필요하다. 계정 자격과 운영 결과는 이 보고서에서 추측하지 않는다.

이 작업의 운영 HTTP·DB 접속, 브라우저·실계정 조작, 이메일 발송, 데이터 쓰기·삭제, 비밀 파일 열기, dev 서버, Git 변경은 모두 0건이다. 소스·스키마·설정은 수정하지 않았고 이 보고서 한 파일만 작성했다.
