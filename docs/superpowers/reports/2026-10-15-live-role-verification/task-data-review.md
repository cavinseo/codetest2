### 실행 전 보존 전제.

- 전체 삭제 직전에도 현재 프로젝트의 응답자 목록이 이번 3명뿐인지 다시 확인한다. 기존 실응답이 보이거나 다른 사용자가 제출했다면 전체 삭제 검증을 중단한다.

### 가장 단순한 3명 입력 형식.

설문 관리의 파일 수집 화면에서 형식을 **전용 양식**으로 선택하고 **양식 받기**를 사용한다. 다운로드 계약은 `GET /api/projects/{projectId}/kano/upload-template?format=template`이다. 루트만 로그인한 브라우저에서 이 경로를 사용한다.

원본 `.xlsx` 통합 문서에는 다음 시트가 있다.

| 시트 | 처리 방법 |
| --- | --- |
| `Kano응답업로드` | 1~3행을 유지하고, 4행의 예시를 아래 검증 응답으로 교체한다. |
| `Kano질문목록` | 그대로 보존한다. 문항 순번과 문항 내용을 확인하는 용도다. |
| `응답점수안내` | 그대로 보존한다. |
| `Kano문항연결` | 반드시 보존한다. `No`, `requirementId`와 모든 문항 ID를 수정하지 않는다. |

`Kano응답업로드`의 정확한 배열 구조는 다음과 같다. `N`은 내려받은 양식의 문항 수다.

```text
1행: [프로젝트명 + " Kano 응답 업로드 양식"]
2행: ["각 응답자는 한 행에 입력하고, 답변 칸에는 1~5 점수를 입력하세요."]
3행: ["email", "Q1_positive", "Q1_negative", ..., "QN_positive", "QN_negative"]
4행: ["codex-role-20261015-<run>-a@example.test", 1, 5, ..., 1, 5]
5행: ["codex-role-20261015-<run>-b@example.test", 1, 3, ..., 1, 3]
6행: ["codex-role-20261015-<run>-c@example.test", 3, 5, ..., 3, 5]
```

`<run>`은 루트가 정하는 이번 실행의 고유한 영문·숫자 식별값으로 바꾼다. 세 응답자 키는 서로 달라야 하며 검증 중 대소문자와 철자를 유지한다. 모든 문항의 긍정·부정 칸에 **정수 숫자**를 채운다. 빈 칸·수식·소수·응답자 키가 중복된 행은 만들지 않는다. 파서는 답변쌍이 유효한 문항만 저장하므로 빈 칸이 있으면 3명이라도 `3N`개 응답을 검증할 수 없다.

메모리 작업은 원본 XLSX 바이트를 workbook으로 읽고, `Kano응답업로드`만 위 배열로 교체한 뒤 다시 XLSX 바이트로 직렬화하는 방식이다. 다른 시트와 `Kano문항연결`의 ID 배열을 그대로 유지한다. 출력 파일 이름은 예를 들어 `kano-role-20261015-<run>-three.xlsx`로 하고, MIME은 `application/vnd.openxmlformats-officedocument.spreadsheetml.sheet`로 전달한다. 응답자 1명 재수집용 파일은 같은 원본 양식의 1~3행과 해당 응답자 1행만 포함한다.

이 보고서는 파일을 만들거나 다운로드하지 않았다. 루트의 브라우저 업로드 도구가 메모리 바이트를 파일 입력에 전달할 수 있는지는 아직 검증하지 않았다. 실제 도구의 지원 형식에 맞춰 루트가 준비한다.

브라우저의 파일 입력에서 `.xlsx`를 선택하고 **업로드 → 기존 데이터에 추가**를 누른다. 이 선택은 `POST /api/projects/{projectId}/kano/upload-excel`에 `file`, `format=template`, `writePolicy=append`를 보낸다. `replaceExistingRespondents`는 보내지 않는다. 파일 크기 제한은 10 MiB다.

### 저장·선택 삭제·전체 삭제·재수집 관찰점.

두 역할 각각에 대해 다음 순서를 적용할 수 있다. 동일 프로젝트를 두 역할이 검증한다면 앞 역할의 마지막 상태를 확인한 다음 다음 역할의 작업을 시작한다.

| 단계 | 조작과 성공 기준 |
| --- | --- |
| 기준 확인 | 현재 프로젝트의 응답이 비어 있고, 요구사항 `N`개와 ID가 확정되어 있다. 계정의 역할 및 프로젝트 관계는 루트가 확인한다. |
| 3명 추가 | 위 파일을 추가 정책으로 업로드한다. 성공 응답의 `respondentCount=3`, `importedCount=3N`과 새로고침 후 3명 목록을 확인한다. 각 문항에서 a는 `1/5 → O`, b는 `1/3 → A`, c는 `3/5 → M`이다. 초대 목록에는 3명의 완료 상태가 생긴다. |
| 선택 취소 | a를 선택하고 삭제 확인을 취소한다. DELETE가 발생하지 않고 3명 목록과 선택이 유지된다. |
| a 선택 삭제 | 요청 본문은 `{"respondentEmails":["실제 a 식별값"]}`이다. `deletedResponses=N`, `resetInvitations=1`, `deletedInvitations=0`을 기대한다. b와 c의 모든 문항이 그대로 남고, 초대 3개 중 a만 미완료가 된다. |
| a 재수집 | a만 담은 파일을 추가 정책으로 업로드한다. `respondentCount=1`, `importedCount=N`을 기대한다. 기존 a 초대가 다시 완료되고 응답자는 3명으로 돌아온다. b·c가 포함된 3명 파일을 이 단계에 쓰면 중복 충돌이 난다. |
| 전체 취소 | 현재 목록이 검증 3명뿐임을 확인하고 전체 삭제 확인을 취소한다. 요청과 목록 변화가 없어야 한다. |
| 전체 응답 삭제 | 본문 없는 DELETE이며 `includeInvitations=true`가 없어야 한다. `deletedResponses=3N`, `resetInvitations=3`, `deletedInvitations=0`을 기대한다. 새로고침 후 응답자 목록은 비고 초대 3개는 모두 미완료로 남는다. |
| 3명 재수집 | 원래 3명 파일을 추가 정책으로 업로드한다. 다시 3명·`3N`개 응답과 완료 초대 3개를 확인한다. |

멘토가 상세 분석을 볼 수 있다면 문항마다 `O=1`, `A=1`, `M=1`, `total=3`을 추가 확인할 수 있다. 동률의 대표 유형을 O로 기대하지 않는다. 멘티의 검증은 응답자 목록·저장 결과·초대 완료 상태를 기준으로 하고 상세 분석 권한을 요구하지 않는다.

각 쓰기 후 실제 화면 새로고침 또는 새 페이지 진입으로 다시 읽은 결과를 확인한다. 로컬 편집값이나 성공 토스트만으로 저장·원복을 판정하지 않는다. 재조회가 실패하면 다음 삭제나 재업로드를 진행하지 않고 관찰 실패로 기록한다. 업로드 중복 409가 나면 저장된 목록을 먼저 확인하며 자동으로 교체 정책을 선택하지 않는다.

재수집은 답변과 완료 상태를 다시 만들 수 있다는 뜻이다. 삭제된 응답 레코드의 ID와 `respondedAt`까지 이전 값으로 복원하는 기능은 없다. 응답만 삭제한 경우 기존 초대는 유지되며, 재업로드는 그 초대를 upsert하여 완료 상태로 갱신한다. 검증 종료 뒤 응답을 비우더라도 새로 만든 초대 3개는 남는다. 이 잔여 상태는 루트가 최종 보고에 기록해야 한다.

### 요구사항 저장과 원복 조건.

Kano 화면의 질문 저장은 질문 1개만 고쳐도 모든 요구사항을 `POST /api/projects/{projectId}/requirements`로 보낸다. ID·분류·항목명·가중치·순서를 포함한 전체 목록이다. API는 제출되지 않은 기존 ID를 삭제하며 요구사항 삭제는 Kano 응답과 QFD 연결 데이터에 cascade로 영향을 줄 수 있다. 검증은 **기존 전체 ID를 유지한 질문 문자열 편집**으로 제한한다.

가장 단순한 검증은 테스트 전용 요구사항 1개의 긍정 질문 끝에 고유 검증 표식을 붙여 저장하고, 새로고침 후 표식을 확인한 뒤 원래 값으로 돌리는 것이다. 시작 전에 루트가 브라우저에서 받아 본 전체 요구사항 목록과 `kanoPositiveQ`, `kanoNegativeQ`의 원래 값을 기록해야 한다. 화면 문구만 기록하면 `null`과 기본 문구의 차이가 사라진다.

| 원래 저장값 | UI 원복 방법과 한계 |
| --- | --- |
| 비어 있지 않은 문자열 | 원래 문자열을 입력하고 저장한다. 새로 읽은 값으로 확인한다. |
| `null` | 해당 textarea를 비우고 저장하면 `|| null`에 의해 null로 전송된다. 기본 문구를 다시 입력하는 것은 null 원복이 아니다. |
| 빈 문자열 `""` | 비워 저장해도 null로 전송된다. 이 UI만으로 값까지 동일한 원복을 보장하지 못한다. |

질문 저장은 원래 null인 다른 항목도 화면 기본 질문 문자열로 보낼 수 있다. 정확한 원복을 원하면 **원래 null인 모든 긍정·부정 칸을 함께 비우고**, 나머지는 원래 문자열을 유지한 전체 목록으로 저장해야 한다. 빈 문자열이 원래 값인 항목이 있으면 이 UI 경로의 원복 한계를 먼저 루트가 사용자와 정리해야 한다. 테스트 데이터의 초기 질문을 명시적인 문자열로 정해 두면 이 구분이 가장 단순하다.

멘티의 일반 저장은 멘토 분석 가중치를 쓰지 않도록 API가 `kanoWeight` 갱신을 제외한다. 배정 멘토는 해당 가중치를 갱신할 수 있으므로 검증 전후 가중치도 함께 비교하고 수정하지 않는다. 요구사항 ID 삭제·재생성·개수 변경·전체 교체와 cascade 확인은 실행하지 않는다. `needsCascadeConfirm`이 발생하면 예상한 단순 편집 경로가 아니므로 중단한다.

심각도가 높은 순서로 정리했다.

1. **P1 · 검증 프로젝트에 기존 응답이 섞이면 전체 삭제가 실데이터를 삭제한다.** 응답 전체 삭제는 화면의 3명 스냅샷이 아닌 현재 프로젝트 전체를 대상으로 한다. 별도 테스트 프로젝트와 전체 삭제 직전 목록 재확인이 필요하다. 동시 제출도 없어야 한다.
2. **P1 · 업로드의 replace는 응답뿐 아니라 초대도 모두 삭제한다.** ‘기존 데이터 지우고 업로드’는 projectId 전체의 응답·초대를 지우고 새 초대를 만든다. 같은 응답자 교체도 해당 응답자의 모든 기존 문항 응답을 삭제한다. 이 검증은 append만 사용한다.
3. **P1 · 요구사항 ID 누락·교체는 cascade로 응답과 연결 자료를 잃게 할 수 있다.** 이름을 나중에 되돌려도 삭제된 응답은 복원되지 않는다. 전체 기존 ID를 보존한 질문 편집과 원복만 사용한다.
4. **P2 · 질문의 화면 문구와 저장값이 다를 수 있다.** null은 기본 질문으로 보이며, 저장은 모든 항목을 보낸다. 원래 null인 모든 칸의 복원이 필요하고 원래 빈 문자열은 UI의 `|| null` 때문에 정확한 값 원복이 불가능하다.
5. **P2 · 선택 삭제 후 원래 3명 파일을 추가하면 남은 2명 때문에 전체 업로드가 409로 거부된다.** 삭제된 1명만 담은 파일로 재수집한다. 같은 파일에 동일 응답자 행을 반복하거나 겹치는 업로드를 동시에 보내지 않는다. 운영 KanoResponse에는 응답자·문항 조합의 unique 제약이 없어 잘못된 입력이나 동시 요청의 중복까지 보장해 주지 않는다.
6. **P2 · 재수집은 원래 레코드의 완전 복원이 아니다.** 응답 ID와 응답 시각은 새로 생기며, 응답만 정리하면 새 초대 레코드가 남는다. 검증용 새 데이터만 조작한다는 전제가 이 차이를 허용해야 한다.
7. **P3 · 실제 계정·프로젝트·브라우저의 메모리 파일 업로드 가능 여부는 아직 미확인이다.** 로그인과 프로젝트 지정 답변 뒤 루트가 확인할 항목이며, 이 보고서는 운영 실행 성공을 주장하지 않는다.
