## 자동 가입을 하지 않은 이유

콜백 첫 줄이 정책을 못박고 있다 — *"승인된 기존 회원만 로그인시킨다 — 자동 가입 없음."*
그리고 가입 API 를 보면 그 정책이 무엇을 지키는지 드러난다.

```ts
status: invite ? 'APPROVED' : 'PENDING',
```

**승인 게이트가 이 시스템의 유일한 방벽이다.** Google 인증만으로 계정을 만들면
`PENDING` 으로 만들더라도 승인 대기 큐가 오염되고, 가입 API 가 rate limit
(`SIGNUP_RATE_LIMIT`)까지 걸어 막아 둔 경로를 Google 로 우회하는 셈이 된다.

그래서 이 Task 가 하는 일은 **안내와 자동 입력뿐**이다.

## URL 이 아니라 쿠키인 이유

이메일은 PII 다. `lib/logger.ts` 가 *"이메일·비밀번호·토큰 등 PII 를 절대 기록하지
않습니다"* 라고 규칙을 세워 두었는데, **URL 은 브라우저 방문 기록과 Referer 에 남는다.**

`next/font/google` 은 빌드 시 자체 호스팅이라 폰트를 통한 Referer 유출은 없음을
확인했다. 그래도 방문 기록에 이메일이 쌓이는 것은 이 저장소의 방침과 맞지 않는다.

이 흐름은 이미 같은 형태의 단기 스코프 쿠키(`google_login_state`)를 쓰고 있어
낯선 방식도 아니다.

`httpOnly` 가 아닌 이유는 가입 화면(클라이언트 컴포넌트)이 직접 읽어야 해서다.
값은 그 브라우저 사용자 본인의 이메일이고, 같은 출처 스크립트만 읽을 수 있다.
세션 쿠키는 `httpOnly` 로 그대로 둔다.

## 쿠키가 특권이 되지 않게 한 장치

프리필이 **신뢰의 근거로 바뀌는 것**이 이 변경의 유일한 위험이다. 지금은 무해하지만,
나중에 누군가 *"Google 에서 온 거니까 이메일 검증은 건너뛰자"* 라고 판단하는 순간
구멍이 된다. 그 판단을 사람의 기억이 아니라 게이트에 맡겼다.

```yaml
- name: Signup approval gate untouched
  run: |
    if grep -q "signup-prefill\|SIGNUP_EMAIL_COOKIE" app/api/auth/signup/route.ts; then
      echo "가입 API 가 프리필 쿠키를 읽고 있다."; exit 1
    fi
    grep -q "status: invite ? 'APPROVED' : 'PENDING'" app/api/auth/signup/route.ts || exit 1
```

**가입 API 가 이 쿠키를 읽기 시작하면 CI 가 깨진다.**

## RISKS

**화면에서 확인하지 않았다.** 이 Task 는 **순수하게 UI 흐름 변경**이라 판정 레시피
6번(화면 검증 3단계)이 반드시 필요하다. 테스트가 덮은 것은 쿠키 파싱 규칙뿐이고,
"배너가 실제로 뜨는가", "가입 화면에 채워지는가"는 브라우저에서만 보인다.
검증 지시서에 V-10~V-12 로 추가했다.

**쿠키 수명 5분은 임의의 수다.** 로그인 실패 직후 곧바로 가입으로 넘어가는 경우만
덮으면 되므로 넉넉하다고 보았지만, 실측 근거는 없다.

**Google 계정이 여러 개인 경우를 확인하지 않았다.** `prompt=select_account` 로 계정을
고르게 되어 있는데, 고른 계정과 프리필된 이메일이 일치하는지는 실기동에서만 보인다.
