## 왜 뒤늦게 했는가

정본 감리 스킬을 설치하고 판정 레시피에 비춰 보니 **3단계를 통째로 건너뛰고 있었다.**

> **3. 회귀 테스트 역검증**: 새 회귀 테스트가 결함을 실제로 잡는지 — 수정만 임시로
> 되돌린 상태에서 그 테스트가 실패하는지 확인 후 원복. **수정 전에도 통과하는 테스트는
> 회귀 테스트가 아니다.**

Task A~E 에서 회귀 테스트 47건을 넣고 "1101개 통과"를 보고했지만, 그중 어느 것도
수정 전에 실패하는지 확인하지 않았다. 합리화 금지 표의 다섯째 줄에 정확히 걸린다 —
*"테스트를 추가했다니 회귀는 잡힐 것" → 수정 전에도 통과하는 테스트는 아무것도 잡지
않는다.*

## 판정 — 전부 통과

기준선이 그린인지부터 확인했다. 여기가 빨간불이면 아래 결과를 해석할 수 없다.

```
===== 기준선 =====
 Test Files  95 passed (95)
      Tests  1101 passed (1101)
```

각 시나리오는 **수정만 되돌리고** 그 결함을 잡으라고 넣은 테스트를 이름으로 지목해
돌렸다. 실패해야 정상이다.

```
===== 역검증 =====

B-1   WS-3 전량 deleteMany 를 되살린다          OK — 결함을 잡는다
      대상: 제출에서 빠진 행만 지운다

      대상: core 가 다르면 sub 이름이 같아도 두 행 모두 칸을 그린다
```

### 신설 순수 모듈은 뮤테이션으로 대신했다

`lib/unsaved-changes.ts`(Task D·E)는 되돌릴 예전 코드가 없다. 그 경우의 등가 검증은
뮤테이션이다 — 테스트가 실행만 하는지, 단언까지 하는지를 본다.

```
===== 신설 모듈 뮤테이션 =====
All files           | 100.00 |  100.00 |       20 |         0 |          0 |        0 |        0 |
 unsaved-changes.ts | 100.00 |  100.00 |       20 |         0 |          0 |        0 |        0 |
```

`lib/import-cascade-guard.ts`(Task B)는 앞서 100%(71 killed, 0 survived)를 확인했다.

## 거짓 결론을 막은 장치

역검증에서 가장 위험한 실패는 "치환이 조용히 빗나가 테스트가 통과하고, 그것을
**회귀를 못 잡는다**로 읽는 것"이다. 그건 검증이 없는 것보다 나쁘다 — 멀쩡한 테스트를
의심하게 만든다.

- 치환 대상이 파일에 **정확히 한 번** 나오지 않으면 스크립트가 즉시 죽는다(개수를 먼저 센다)
- 지목한 테스트가 하나도 실행되지 않으면(이름 불일치) `판정불가`로 따로 표시한다 —
  `통과`와 섞지 않는다
- 원복은 테스트 결과와 무관하게 항상 실행하고, 워크플로가 `git status -- app lib` 로
  다시 확인한다. 중간에 죽으면 다음 시나리오가 오염된 파일 위에서 돈다

로컬에서 5건 모두 1회 매칭을 미리 확인한 뒤 CI 에 올렸다.
