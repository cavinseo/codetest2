# 통합 테스트 수동 실행 절차 (감리자용)

**결정:** 감리자가 로컬에서 한 번 수동으로 돌린다(CI 편입은 하지 않는다).

## ⚠️ 먼저 — 앞선 설명을 한 가지 정정한다

판단을 요청하면서 "실DB 접속이 필요해 환경 제약과 부딪힌다"고 적었는데, **정확하지
않았다.** 이 테스트는 **실데이터 DB에 붙지 않는다.** 코드에 안전장치가 둘 박혀 있다
(`tests/integration/db-cascade.integration.test.ts:14-45`).

| 안전장치 | 하는 일 |
| --- | --- |
| 1 | `INTEGRATION_DATABASE_URL` 이 없으면 **모듈 로드 시점에** 즉시 실패한다. `PrismaClient` 생성조차 되지 않는다 |
| 2 | 그 값이 앱의 `POSTGRES_PRISMA_URL` 과 **바이트 단위로 같으면** 실패한다 |

즉 **일회용 테스트 전용 Postgres 를 따로 띄워야만 돈다.** 실수로 실DB를 가리키는 사고는
코드가 막는다. 다만 "그 URL이 진짜 일회용 DB인가"는 여전히 실행하는 사람이 확인해야 한다.

이 정정 때문에 선택이 달라진다면 알려주면 된다 — CI에 임시 Postgres를 붙이는 3번 안도
생각보다 안전하다.

## 무엇을 확인하는가

```
FK 와 캐스케이드 실측
  존재하지 않는 사용자 ID 로 초대를 만들 수 없다
  실재하는 사용자 ID 로는 초대를 만들 수 있다
  요구사항을 지우면 Kano 응답이 함께 사라진다
  속성을 지우면 적합도가 함께 사라진다        ← Task B 가 딛고 선 전제
  응답이 있는 프로젝트도 삭제할 수 있다
```

**네 번째가 이번 작업과 직결된다.** Task B 는 "`deleteMany` 가 캐스케이드로 적합도를
지운다"를 전제로, 그러니 **보존할 행은 지우지 말자**로 고친 것이다. 그 전제가 진짜
DB에서도 사실인지 확인하는 테스트다.

## 실행 절차

### 1. 일회용 Postgres 를 띄운다

Docker 가 있으면 가장 간단하다.

```sh
docker run --rm -d --name codetest2-it -p 5433:5432 \
  -e POSTGRES_PASSWORD=it -e POSTGRES_USER=it -e POSTGRES_DB=it postgres:16
```

포트를 5433 으로 둔 이유는 로컬에 이미 도는 Postgres 와 겹치지 않게 하기 위해서다.

### 2. 스키마를 올린다

**이 명령은 1번에서 띄운 일회용 DB에만 쓴다.** `.env` 의 값이 새어 들어가지 않도록
환경변수를 명령 앞에 직접 붙인다.

```sh
DATABASE_URL="postgresql://it:it@localhost:5433/it?schema=public" \
POSTGRES_PRISMA_URL="postgresql://it:it@localhost:5433/it?schema=public" \
POSTGRES_URL_NON_POOLING="postgresql://it:it@localhost:5433/it?schema=public" \
npx prisma db push --skip-generate
```

> `db push` 는 CLAUDE.md 가 금지한 명령이다. **그 금지는 실데이터 DB를 향한 것이고**,
> 여기서는 방금 만든 빈 컨테이너를 가리킨다. 실행 전에 URL이 `localhost:5433` 인지
> 눈으로 한 번 확인한다.

### 3. 테스트를 돌린다

```sh
INTEGRATION_DATABASE_URL="postgresql://it:it@localhost:5433/it?schema=public" \
npm run test:integration
```

`POSTGRES_PRISMA_URL` 은 `.env` 값 그대로 두면 된다 — 안전장치 2가 두 값이 다른지
확인하는 데 쓰인다.

### 4. 정리한다

```sh
docker rm -f codetest2-it
```

## 기대 결과

```
 Test Files  1 passed (1)
      Tests  5 passed (5)
```

**하나라도 실패하면 알려주기 바란다.** 특히 `속성을 지우면 적합도가 함께 사라진다` 가
실패하면 Task B 의 전제가 흔들리는 것이라, 고친 방향 자체를 다시 봐야 한다.

## 이 테스트가 확인하지 **않는** 것

**Task B 가 새로 만든 동작은 여기 없다.** 이 파일은 "DB 수준의 캐스케이드가 실제로
일어나는가"만 본다. "라우트가 빠진 행만 지우는가"는 mock 테스트
(`tests/api-worksheet-cascade.test.ts`)에만 있다.

진짜 DB에서 그것까지 확인하려면 통합 테스트를 새로 써야 한다 — 속성 3개를 만들고,
적합도를 달고, 한 행만 빼고 저장한 뒤, **나머지 두 행의 적합도가 살아 있는지** 보는
테스트다. 필요하다고 판단되면 별건으로 요청하면 된다.
