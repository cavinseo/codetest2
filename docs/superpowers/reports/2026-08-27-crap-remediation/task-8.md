# Task 8 결과 보고서 — CRAP 상시화

## RESULT

측정 장치가 **PR 에서 자동으로 돌고, 위험이 생기면 CI 를 세운다.**

이번 계획으로 CRAP 위험을 12건에서 0건으로 만들었지만, 그것만으로는 다음 달에 다시
쌓이는 것을 막지 못한다. `crap.yml` 은 `claude/**` 브랜치에서만 돌았고, main 에
병합된 뒤에는 아무도 재지 않기 때문이다. 커버리지 없는 함수가 새로 들어와도 `tsc`·
`test`·`lint`·`build` 는 전부 정상이라 CI 는 초록불이다.

| 항목 | 이전 | 이후 |

| 측정 결과가 없을 때 | (해당 없음) | **실패** (닫는 쪽) |

### D-3 결정 — PR 트리거

회귀는 결국 코드가 main 으로 들어올 때 생기고 그 관문이 PR 이다. 거기서만 재면
비용은 거의 들지 않으면서 목적은 달성된다. `ci.yml` 에 합치는 안은 모든 푸시가 약
4분 길어지는데(이번 세션 실측), 그 대가로 얻는 것이 없어 택하지 않았다.

`workflow_dispatch` 는 남겨 두어 필요할 때 손으로 돌릴 수 있다.

### 실패 조건 — `--fail-over=30`

`scripts/crap-report.mjs` 에 임계값 옵션을 더했다. 30 은 CRAP 원 논문의 기준선이고,
Phase 2 에서 위험을 0건으로 만들어 둔 상태가 그대로 기준선이 된다.

**측정 결과가 아예 없을 때도 통과시키지 않는다.** 커버리지 수집이 실패해 데이터가
없는데 초록불이 나오면 게이트가 있으나 마나이므로, 닫는 쪽으로 실패한다.

## DEVIATIONS

**검증을 위해 `push: claude/**` 트리거를 한 번 더 남겼다가 지웠다.** PR 트리거만
남기면 PR 이 없는 상태에서는 게이트가 실제 데이터로 도는지 확인할 수 없다. 그래서
커밋 `1636a16` 에는 푸시 트리거를 남겨 한 번 돌리고, 확인한 뒤 이 커밋에서 지웠다.

그 결과 **이 마지막 커밋 자체는 CI 를 거치지 않는다.** 변경이 문서와 워크플로 파일
뿐이라 게이트에 영향이 없어 그대로 둔다.

## RISKS

**PR 없이 main 에 직접 푸시하면 측정되지 않는다.** D-3 에서 그 대가를 알고 고른
방식이지만, 저장소에 브랜치 보호가 걸려 있지 않다면 우회가 가능하다는 점은 남는다.
막으려면 main 에 "PR 필수" 보호 규칙이 필요한데, 저장소 설정 변경이라 코드로 할 수
없다.

## QUESTIONS

**`--fail-over` 는 CRAP 만 본다. 뮤테이션 점수에는 임계값이 없다.**

지금 뮤테이션은 숫자만 남기고 CI 를 세우지 않는다. 이유가 있다 — Task 7 에서 드러난
static mutant 문제 때문에 파일별 점수를 액면 그대로 임계값에 걸면 오탐이 난다
(`bulk-save-schemas.ts` 의 65.5% 에는 모듈 평가 시점 뮤턴트가 섞여 있다).

전체 점수에 하한(예: 95%)을 거는 정도는 지금도 가능하다. 다만 대상을 넓힐 때마다
점수가 내려가므로(Task 6 에서 95.32% → 95.19%), 하한을 걸면 **대상을 넓히는 일 자체가
CI 를 깨는** 역효과가 난다. 그래서 이번에는 걸지 않았다. 판단을 요청한다.
