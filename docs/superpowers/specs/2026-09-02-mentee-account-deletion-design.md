# 멘티 계정 삭제 지침 설계

**작성일:** 2026-09-02
**대상 브랜치:** `claude/admin-account-password-recovery-o93xgy`
**상태:** 결정 완료(9절), 구현 계획서 작성 대기

## 1. 배경과 문제

멘티는 이 서비스에서 데이터를 가장 많이 만드는 역할이다. 초대 코드로 가입해 프로그램에 묶이고(`User.programId`), 프로젝트를 만들고, Kano 설문을 발송하고, 엑셀 워크북을 가져온다. 그래서 멘티 계정을 지우는 일은 "행 하나를 지우는 일"이 아니라 "그 사람이 남긴 것 중 무엇을 남기고 무엇을 없앨지 정하는 일"이다.

### 1.1 지금의 삭제 흐름

`DELETE /api/admin/users` 는 대상이 멘티면 다른 역할과 다른 길을 탄다(`app/api/admin/users/route.ts:398`). 소유 프로젝트의 `ownerId` 를 그 프로젝트가 속한 프로그램의 매니저로 옮긴 뒤 `user.delete` 를 실행한다. 프로그램은 멘티들의 프로젝트로 구성되므로 사람이 빠졌다고 작업물이 사라지면 안 된다는 판단이고, 그 판단은 옳다. 프로젝트 이전과 삭제는 배열형 `$transaction` 이라 한쪽이 실패하면 둘 다 되감긴다. 파괴적이지 않다는 이유로 추가 확인을 묻지 않는다(`lib/delete-confirmation.ts:8`).

`user.delete` 는 스키마에 적힌 대로 연쇄 반응을 일으킨다.

| 동작 | 대상 |
| --- | --- |
| 함께 삭제 (Cascade) | 프로젝트 멤버십, 회원 프로필, AI 연결 설정, 발급한 초대 코드 |
| 연결만 끊음 (SetNull) | 사용한 초대 코드의 `usedById` (`prisma/schema.prisma:540`) |
| 삭제를 거부 (Restrict) | 설문 초대 발송 이력 `KanoSurveyInvitation.invitedBy` (`:252`), 엑셀 가져오기 이력 `MigrationHistory.userId` (`:367`), 담당 중인 프로그램 `Program.managerId` (`:66`) |

### 1.2 실제 격차

**설문을 한 번이라도 보냈거나 엑셀을 한 번이라도 가져온 멘티는 지울 수 없다.** 세 번째 줄의 Restrict 가 `P2003` 을 던지고, 서버는 "승인을 취소해 접근만 막아 주세요"라고 안내한다(`route.ts:443`). 멘티는 설문 발송과 가져오기를 하라고 있는 역할이므로, 실질적으로 **활동한 멘티는 전부 삭제 불가**다.

그 위에 다음 문제가 겹친다.

- **이력만 지울 수는 없다.** `KanoResponse.invitationId` 도 Restrict 라(`schema.prisma:270`) 초대를 지우려면 응답부터 지워야 하고, 응답은 Kano 분석의 원천이다. 현재 있는 리셋 기능(`lib/kano-response-reset.ts`)이 정확히 그 순서로 지운다. 즉 지금 구조에서 "삭제"를 관철하려면 설문 결과를 버려야 한다.
- **막는 이력이 화면에 나오지 않는다.** `invitedBy` 는 쓰기만 하고 초대 목록 API 도 돌려주지 않는다(`app/api/projects/[id]/kano/invitations/route.ts:24`). `MigrationHistory` 는 테이블 전체를 읽는 코드가 한 줄도 없다(`app/api/projects/[id]/import/route.ts:193` 에서 생성만 한다). 아무도 보지 않는 기록이 삭제를 막고 있다.
- **멘티도 트랜잭션이 통째로 되감긴다.** 프로젝트 이전까지 계산한 뒤 삭제에서 `P2003` 이 나면 이전도 취소되고, 화면에는 설문 이력 문구만 남는다. 관리자는 무엇이 바뀌었는지 알 수 없다.
- **오류 문구가 원인을 오진한다.** 프로그램 매니저를 겸하는 계정이 막혀도 같은 설문 이력 문구가 나온다. 멘티는 매니저가 될 수 없어(`lib/member-roles.ts` 의 `canTransitionRole`) 이 문서의 범위 밖이지만, 같은 라우트를 고치는 김에 함께 바로잡는다.
- **개인정보가 하나 남는다.** 멘티가 사용한 초대 코드는 `usedById` 만 비워지고 `InviteCode.email` 은 그대로 남는다. 계정을 지워도 그 사람의 이메일이 DB 에 남는 유일한 자리다.
- **프로그램 종료는 아무것도 바꾸지 않는다.** `Program.endsAt` 은 표시에만 쓰인다(`app/profile/page.tsx:29`, `app/api/programs/route.ts:104`). 멘티의 접근을 실제로 끊는 것은 초대 코드에서 온 `accessExpiresAt`(기본 90일, `schema.prisma` `InviteCode.accessDurationDays`)뿐이다. 프로그램이 끝나도 기간이 남은 멘티는 그대로 활동하고, 기간이 끝난 멘티는 로그인만 막힌 채 계정과 데이터가 무기한 남는다.

이 문서는 "언제 지우고 언제 지우지 않을지"의 지침과, 지우기로 했을 때 실제로 지워지게 만드는 구현 전략을 정한다.

## 2. 지침

### 2.1 경계

**멘티 계정은 막는 것이 기본이고, 지우는 것은 개인정보를 파기해야 할 때만 한다.**

프로그램 종료, 이용 기간 만료, 중도 이탈, 문제 행동은 모두 **승인 취소**(또는 만료 방치)로 끝낸다. 승인 취소는 `status=PENDING` 과 `sessionVersion+1` 로 로그인과 기존 세션을 즉시 끊고(`route.ts:182`), 데이터는 한 줄도 건드리지 않는다. 접근을 막는 목적이라면 삭제가 승인 취소보다 나은 점이 없다.

**삭제**는 다음 두 경우에만 한다.

1. **본인의 삭제 요청.** 정보주체가 계정 삭제나 개인정보 파기를 요구하면 지체 없이 파기한다(개인정보보호법의 파기·삭제 요구 원칙. 조문 적용은 법률 검토로 확인 필요).
2. **오등록.** 잘못 만든 계정, 테스트 계정처럼 활동 기록이 없거나 보존할 이유가 없는 계정.

세 번째 후보인 **보유기간 경과**(만료 후 일정 기간이 지난 계정의 일괄 파기)는 **이번에 만들지 않는다**(9절 확정 1). 기준이 될 정책 값을 지금 잘못 정하면 되돌리기가 더 번거롭다. 대신 삭제 사유 항목에 `retention_expired` 를 미리 열어 두어, 프로그램 한 기수를 운영해 본 뒤 정책이 정해지면 같은 삭제 경로를 일괄로 부르는 것만 추가하면 되도록 설계한다.

### 2.2 원칙

- **작업물은 프로그램의 것, 개인정보는 사람의 것이다.** 프로젝트·워크시트·설문 응답은 프로그램에 남긴다. 이름·이메일·연락처·소속·AI 키는 사람과 함께 사라진다. 이 구분이 데이터 처리표(3절)의 유일한 기준이다.
- **이력은 남기되 주인을 지운다.** 설문 발송과 가져오기 기록은 "언제 무엇을 했는가"가 가치이고 "누가"는 개인정보다. 기록을 보존하고 발신자만 비운다(`SetNull`). 남의 이름으로 바꾸지 않는다. 감사 추적을 틀어 놓는 일이라서다.
- **제3자 정보는 이 삭제의 대상이 아니다.** 설문 응답자의 이메일(`KanoSurveyInvitation.email`, `KanoResponse.respondentEmail`)은 멘티가 아니라 응답자의 정보이고 프로젝트에 귀속된다. 멘티 삭제로 건드리지 않는다. 응답자 정보의 보유기간은 별도 설계 문서로 다룬다(9절 확정 4).
- **지우기 전에 무엇이 벌어질지 보여 준다.** 관리자는 "프로젝트 N개가 매니저 X 에게 넘어가고, 초대 M건과 가져오기 K건의 발신자가 비워진다"를 보고 결정한다. 지금처럼 결과가 나온 뒤에야 아는 구조를 없앤다.
- **삭제는 사유와 함께 기록한다.** 누가 언제 어떤 사유로 지웠는지를 로그에 남기되, 이메일은 남기지 않는다(`lib/logger.ts` 규칙). 파기 사실의 증빙은 삭제된 정보 자체가 아니라 그 기록이다.
- **권한은 관리자만.** 회원 삭제는 관리자 전용이라는 기존 권한표(`2026-08-20-member-management-design.md` 2절)를 그대로 따른다. 매니저는 승인 취소도 삭제도 할 수 없다.

## 3. 데이터 처리표

멘티 한 명이 남기는 데이터 전부다. "현행"은 지금 코드가 이미 그렇게 한다는 뜻이고, "신규"는 이 설계로 바뀌는 항목이다.

| 데이터 | 분류 | 처리 | 비고 |
| --- | --- | --- | --- |
| `User` (email, name, passwordHash) | 개인정보 | 삭제 | 현행 |
| `MemberProfile` (소속·직책·휴대폰·기업명·업종·창업연차·동의시각) | 개인정보 | 삭제 | 현행 Cascade |
| `UserAiConnection` (암호화된 API 키·엔드포인트) | 비밀 | 삭제 | 현행 Cascade |
| 소유 `Project` 와 하위 워크시트 22종 | 프로그램 자산 | 프로그램 매니저에게 이전 | 현행 유지 |
| `ProjectMember` (남의 프로젝트 참여) | 관계 | 삭제 | 현행 Cascade. `invitedBy` 는 FK 없는 문자열이라 id 만 남으며 개인정보가 아니다 |
| `KanoSurveyInvitation.invitedBy` | 이력의 주인 | **익명화 (SetNull)** | 신규. 초대·응답은 보존 |
| `KanoSurveyInvitation.email`, `KanoResponse.respondentEmail` | 제3자 정보 | 보존 | 응답자의 것. 별도 정책 |
| `MigrationHistory.userId` | 이력의 주인 | **익명화 (SetNull)** | 신규. 파일명·시각·결과는 보존 |
| `InviteCode.usedById` | 관계 | SetNull | 현행 |
| `InviteCode.email` (그 사람에게 발급된 코드) | 개인정보 | **삭제** | 신규. 사용 여부와 무관하게 그 이메일로 발급된 코드를 전부 지운다(9절 확정 2) |
| 세션 쿠키 | 접근 | 즉시 무효 | 현행. 행이 없으면 `requireAuth` 가 401 (`lib/auth.ts:132`) |
| 앱 로그 | 기록 | `userId` 와 사유만 | 이메일 금지 |
| DB 덤프 (`scripts/export-current-db-data.mjs` 산출물) | 사본 | 사용 즉시 삭제 | 규칙을 운영 지침에 적는다(9절 확정 5) |
| Supabase 자동 백업 | 사본 | 보존 주기를 문서에 기록 | 백업본 개별 파기는 하지 않는다(9절 확정 5) |

`Program.managerId` 는 이 표에 없다. 멘티는 매니저가 아니다. 프로그램 매니저 계정의 삭제는 담당자 이관이 선행돼야 하는 다른 지침이다.

## 4. 절차

관리자 화면(`/admin` 회원 관리) 기준이다.

| 단계 | 행위자 | 하는 일 |
| --- | --- | --- |
| 0 | 관리자 | 접근만 막을 일인지 먼저 자문한다. 그렇다면 **승인 취소**로 끝낸다 |
| 1 | 관리자 | 행의 **삭제**를 누른다 |
| 2 | 시스템 | 지우지 않고 **사전 점검 결과**를 돌려준다. 이전될 프로젝트 수와 받을 매니저, 발신자가 비워질 초대·가져오기 건수, 지워질 초대 코드 수. 막히는 원인이 있으면(예: 예상 밖의 FK) 원인별 문구 |
| 3 | 관리자 | 확인창에서 결과를 읽고 **사유**(본인 요청 / 오등록 / 보유기간 경과)를 고른 뒤 확정한다 |
| 4 | 시스템 | 한 트랜잭션으로 실행한다. 프로젝트 `ownerId` 이전 → 그 사람에게 발급된 초대 코드 삭제 → `user.delete`. 초대·가져오기 이력의 발신자는 DB 의 `SetNull` 이 비운다 |
| 5 | 시스템 | 로그에 `userId`·사유·이전 프로젝트 수·비워진 이력 수를 남긴다. 화면에 같은 요약을 보여 준다 |
| 6 | 관리자 | 본인 요청이었다면 요청자에게 파기 완료를 알린다(서비스 밖 절차) |

2단계는 다른 역할이 이미 쓰는 `409 needsCascadeConfirm` 되묻기 흐름(`route.ts:421`, `app/admin/page.tsx:125`)과 같은 모양이다. 멘티만 확인 없이 지우던 예외를 없앤다. "파괴적이지 않다"는 근거는 개인정보 파기가 끼는 순간 성립하지 않는다.

## 5. 구현 전략

### 5.1 스키마

두 컬럼을 nullable 로 바꾸고 `onDelete: SetNull` 을 명시한다.

```prisma
model KanoSurveyInvitation {
  // 발송한 사람. 계정이 파기되면 비워진다. 초대·응답은 프로젝트의 것이라 남긴다.
  invitedBy   String?
  inviter     User?          @relation(fields: [invitedBy], references: [id], onDelete: SetNull)
}

model MigrationHistory {
  // 가져온 사람. 계정이 파기되면 비워진다. 무엇을 언제 가져왔는지는 남긴다.
  userId         String?
  user           User?    @relation(fields: [userId], references: [id], onDelete: SetNull)
}
```

마이그레이션 SQL 초안이다. 실제 제약 이름은 `npx prisma migrate dev --create-only` 가 생성한 것을 쓴다.

```sql
ALTER TABLE "kano_survey_invitations" ALTER COLUMN "invitedBy" DROP NOT NULL;
ALTER TABLE "kano_survey_invitations" DROP CONSTRAINT "kano_survey_invitations_invitedBy_fkey";
ALTER TABLE "kano_survey_invitations" ADD CONSTRAINT "kano_survey_invitations_invitedBy_fkey"
    FOREIGN KEY ("invitedBy") REFERENCES "users"("id") ON DELETE SET NULL ON UPDATE CASCADE;

ALTER TABLE "migration_histories" ALTER COLUMN "userId" DROP NOT NULL;
ALTER TABLE "migration_histories" DROP CONSTRAINT "migration_histories_userId_fkey";
ALTER TABLE "migration_histories" ADD CONSTRAINT "migration_histories_userId_fkey"
    FOREIGN KEY ("userId") REFERENCES "users"("id") ON DELETE SET NULL ON UPDATE CASCADE;
```

기존 행은 바뀌지 않는다. 제약 교체는 짧은 잠금으로 끝난다. 되돌리려면 null 인 행을 먼저 처리해야 하므로, 되돌릴 일이 없도록 결정을 먼저 받는다.

`KanoResponse.invitationId` 와 `Program.managerId`, `Project.programId` 의 Restrict 는 **그대로 둔다.** 응답이 초대 없이 남으면 안 되고, 프로그램이 담당자 없이 남으면 안 된다는 판단은 이 설계와 충돌하지 않는다.

`invitedBy` 를 쓰는 코드 다섯 곳(`kano/invite`, `kano/invite/bulk`, `kano/upload-excel`, `kano/form-responses`, `import`)은 모두 로그인한 사용자의 id 를 넣으므로 타입이 `String?` 이 돼도 고칠 것이 없다. 읽는 코드는 없다.

### 5.2 API — `app/api/admin/users/route.ts`

멘티 분기를 다음처럼 바꾼다.

1. **사전 점검.** `confirmCascade` 가 없으면 지우지 않고 409 로 되돌려 준다. 응답에 `needsCascadeConfirm: true` 와 함께 `preview` 를 싣는다. 소유 프로젝트 목록(id·이름·받을 매니저 이름), 초대 건수, 가져오기 건수, 삭제될 초대 코드 수. 이 값들은 `prisma.project.findMany`, `kanoSurveyInvitation.count`, `migrationHistory.count`, `inviteCode.count` 네 번의 읽기로 얻는다.
2. **사유.** `reason` 을 `'self_request' | 'misregistration' | 'retention_expired'` 로 받아 zod 로 검증한다. 확정 요청에 없으면 400. 사전 점검 요청에는 없어도 된다.
3. **실행.** 배열형 `$transaction` 에 `inviteCode.deleteMany({ where: { email: target.email } })` 를 프로젝트 이전 뒤, `user.delete` 앞에 넣는다. `where` 에 사용 여부 조건을 붙이지 않는다. 미사용 코드까지 함께 지우는 것이 확정이며(9절 확정 2), 조건이 하나면 운영자가 헷갈릴 일이 없다. 이메일 비교는 대소문자를 무시한다(`mode: 'insensitive'`). 가입 시 저장된 주소와 코드 발급 시 입력한 주소의 대소문자가 다를 수 있다.
4. **로그.** `log.info('멘티 삭제', { userId, reason, transferredProjects, invitationsAnonymized, migrationsAnonymized })`. 이메일은 넣지 않는다.
5. **오류 문구.** `P2003` 처리(`:443`)를 원인별로 나눈다. 삭제 직전에 이미 읽은 점검 결과가 있으므로, 담당 프로그램이 있으면 "담당 중인 프로그램이 있어 삭제할 수 없습니다. 담당자를 먼저 옮기세요"를, 그 밖에는 "삭제를 막는 연결이 남아 있습니다"와 함께 `P2003` 의 `meta.field_name` 을 로그에 남긴다. 설문·가져오기 문구는 마이그레이션 뒤에는 나올 수 없으므로 없앤다.

다른 역할의 분기(`:421`)는 손대지 않는다. 사전 점검 응답의 모양만 멘티와 맞춘다.

### 5.3 화면 — `app/admin/page.tsx`, `components/admin/MembersTab.tsx`

- `handleDeleteUser` 의 409 처리(`page.tsx:125`)가 `preview` 를 받으면 `window.confirm` 대신 사유 선택이 있는 확인창을 띄운다. 확인창은 프로젝트 목록과 건수를 그대로 보여 준다.
- 확인창 첫 줄에 "접근만 막으려면 승인 취소를 쓰세요"를 고정으로 둔다. 2.1 의 경계를 화면에서 되새기게 하는 장치다.
- `lib/delete-confirmation.ts` 의 주석(`:8`)을 "사용자 삭제는 서버가 409 로 사전 점검 결과를 돌려주는 자체 2단계가 있다"로 고친다. 판정 함수는 그대로다.

### 5.4 권한 — 이전받은 프로젝트에서 매니저의 쓰기

프로젝트가 매니저에게 이전되면 매니저가 `OWNER` 가 된다. `resolveProjectRole` 은 매니저의 명시 역할이 `OWNER` 면 그대로 유지하고(`lib/authorization.ts:37`), `OWNER` 는 쓰기 역할이다. 즉 **이전받은 프로젝트에서는 매니저가 내용을 고칠 수 있다.** "매니저는 내용을 수정할 수 없다"는 원칙과 어긋나는 것처럼 보이지만, 떠난 멘티의 프로젝트를 다른 멘티에게 넘기거나 정리하려면 누군가는 편집할 수 있어야 한다. 이 설계는 **이 예외를 받아들이고 문서로 못 박는다.** 코드는 바꾸지 않는다(9절 확정 3). 프로젝트 목록에서 이전받은 프로젝트임을 알 수 있게 하는 표시는 이번 묶음에 넣지 않고 후속 과제로 남긴다.

### 5.5 스크립트

없다. 사전 점검이 API 에 있으므로 별도 조회 스크립트는 만들지 않는다. 보유기간 일괄 파기를 이번에 만들지 않기로 했으므로(9절 확정 1) 일괄 조회 스크립트도 필요하지 않다. 나중에 정책이 정해지면 `scripts/find-admin.mjs` 와 같은 읽기 전용 조회 스크립트를 먼저 만들고, 실행은 이 API 를 재사용한다.

### 5.6 테스트

- `tests/db-migration-models.test.ts` 방식으로 스키마 문자열을 검사한다. `invitedBy\s+String\?` 과 `onDelete: SetNull` 이 두 모델에 있어야 통과.
- `tests/api-admin-user-delete.test.ts` 의 멘티 묶음(`:142`)을 고친다. 확인 없는 요청은 409 와 `preview` 를 돌려주고 아무것도 지우지 않는다. 확정 요청은 사유가 없으면 400. 확정 요청의 트랜잭션 배열에 초대 코드 삭제가 프로젝트 이전 뒤·사용자 삭제 앞에 있다. 로그 호출에 이메일이 없다.
- `P2003` 이 담당 프로그램 때문일 때 담당자 이관 문구가 나온다.
- `lib/authorization.ts` 의 기존 테스트는 바뀌지 않아야 한다. 5.4 가 코드를 바꾸지 않는다는 증거다.

## 7. 롤아웃

Task 단위다. 각 Task 는 `npx tsc --noEmit && npx vitest run && npx next lint` 를 통과해야 끝난다. **실DB 마이그레이션은 운영자가 직접 실행한다.** 코드 AI 는 마이그레이션 파일과 명령까지만 준비한다.

1. **Task 1 — 스키마.** 5.1 의 변경과 마이그레이션 파일, 스키마 테스트. `npx prisma validate` 와 `npx prisma generate` 로 검증한다. 운영자가 `npx prisma migrate deploy` 를 실행한 뒤 Task 2 로 넘어간다.
2. **Task 2 — API.** 5.2 의 사전 점검·사유·초대 코드 정리·로그·원인별 문구. 테스트 갱신.
3. **Task 3 — 화면.** 5.3 의 확인창. 감리자가 실계정으로 사전 점검 화면과 승인 취소 안내를 확인한다.
4. **Task 4 — 운영 지침 문서.** 이 문서의 2·4절을 운영자용 짧은 지침으로 옮겨 `docs/2026-09-02-admin-account-recovery.md` 옆에 둔다. 여기에 덤프 파일 즉시 삭제 규칙과 Supabase 백업 보존 주기(운영자가 콘솔에서 확인해 알려 준 값)를 함께 적는다(9절 확정 5). 관리자 화면 도움말 링크는 선택.

Task 1 과 2 는 코드만 보면 순서를 바꿔도 되지만, 마이그레이션이 적용되기 전에 Task 2 가 배포되면 활동한 멘티의 삭제는 여전히 막힌다. 그래서 순서를 고정한다.

## 8. 설계 검토 — 대안과 기각 이유

네 가지 관점(데이터 무결성, 개인정보 준수, 최소 변경, 라이프사이클 자동화)에서 안을 세우고 서로 부딪혀 본 결과다. 애초에 4개 안을 독립 에이전트가 세우고 심사·반박하는 방식으로 진행하려 했으나 실행 환경 장애로 무산돼, 같은 틀을 한 사람이 순서대로 적용했다. 그 점을 감안해 읽어야 한다.

| 대안 | 내용 | 판정 |
| --- | --- | --- |
| A. 지금 화면만으로 | 프로젝트별 Kano 리셋으로 초대·응답을 지우고, 가져오기 이력이 있는 프로젝트는 통째로 삭제한 뒤 계정 삭제 | **기각.** 계정 하나 지우자고 설문 결과와 프로젝트를 버린다. "작업물은 프로그램의 것" 원칙에 정면으로 어긋난다 |
| B. 이력의 주인을 관리자로 옮김 | `invitedBy`·`userId` 를 관리자 계정으로 UPDATE 한 뒤 삭제 | **기각.** 스키마를 안 바꿔도 되지만 "관리자가 보낸 설문"이라는 거짓 기록이 생긴다. 감사 추적을 지키려다 감사 추적을 망친다 |
| C. SetNull | 이력 컬럼을 nullable + SetNull | **채택.** 두 컬럼 모두 읽는 곳이 없어 실질 손실이 없고, 원래 의도("이력은 남기되 사람은 지운다")에 맞는다 |
| D. 단계형 라이프사이클 | 만료 → 비활성 → 유예 → 자동 파기 | **일부 채택.** "막는 것이 기본"은 D 에서 왔다. 자동 파기는 보유기간이라는 정책 값이 없어 이번에 만들지 않기로 확정했다(9절 확정 1). 구현은 같은 삭제 경로를 일괄로 부르면 되도록 열어 둔다 |
| 멘티 무확인 삭제 유지 | 현행처럼 멘티는 되묻지 않는다 | **기각.** 개인정보 파기가 끼면 되돌릴 수 없는 조작이다. 사전 점검 없이 지우는 것은 지침의 "지우기 전에 보여 준다" 원칙과 맞지 않는다 |
| 매니저의 이전 프로젝트 쓰기 차단 | `resolveProjectRole` 에서 매니저의 `OWNER` 를 `VIEWER` 로 낮춤 | **기각.** 승격 전에 직접 만든 프로젝트의 소유권까지 잃는다(`lib/authorization.ts:36` 의 결정과 충돌). 떠난 멘티의 프로젝트를 정리할 사람이 없어진다 |
| `InviteCode` 행 유지 + 이메일 마스킹 | 발급 통계를 위해 행을 남기고 `email` 만 가린다 | **보류.** 발급 통계를 보는 화면이 없어 지금은 삭제가 단순하다. 통계가 필요해지면 그때 바꾼다 |

검토에서 새로 드러나 반영한 것은 세 가지다. `InviteCode.email` 이 파기 뒤에도 남는다는 점(3절), 멘티 삭제가 트랜잭션 전체를 되감아 화면이 원인을 못 보여 준다는 점(4절 사전 점검), 이전받은 프로젝트에서 매니저가 쓰기 권한을 얻는다는 점(5.4).

### 9.2 운영자에게 필요한 것

Task 4 를 마치려면 **Supabase 자동 백업의 보존 주기**를 콘솔에서 확인해 알려 줘야 한다(확정 5). 본인에게 파기 완료를 답할 때 "운영 DB 에서 파기했고 백업본은 N일 후 자동 소멸한다"까지 말하려면 이 값이 필요하다.

법률 검토(확정 7)에서 확인받을 것은 세 가지다. 2.1 의 삭제 사유가 충분한지, 이력의 익명화(`SetNull`)를 파기로 볼 수 있는지, 3절의 제3자 정보 보존이 적법한지. 이 문서는 기술 설계이며 법적 판단이 아니다.
