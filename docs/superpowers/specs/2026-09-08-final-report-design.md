**IMG** = 화면을 그림으로 캡처해야 함(관계·그래프 시각화가 복잡해 표로 재현하기 어려움) ·

## 결정 (사용자 확인 완료, 2026-09-08)

1. **출력 형식: `.docx`.** 슬라이드 장식(대각선 띠·배지)은 재현하지 않고 내용 중심으로
   재설계한다. 계획서의 `docx` 라이브러리 아키텍처 그대로 진행.
2. **속성 적합도(6쪽)·Kano 산점도(8쪽)·QFD 관계도(10쪽): 화면 캡처(IMG)로 확정.**
   그림 캡처 대상 워크시트는 **WS-4, WS-7, WS-9 세 곳뿐**이다(당초 계획서가 후보로 뒀던
   WS-10 기술기술체계도는 매핑 결과 순수 표 데이터라 DB 로 재현하므로 제외).

## 나머지 항목 — 감리자 기본안(사용자 이견 없으면 이대로 진행)

블로킹 질문 2개 외에는 재량 범위로 보고 아래처럼 정했다. 각 항목의 판단 근거를 적었으니
다르게 하고 싶으면 알려 달라.

3. **"최종 목표 스펙 설명"(11쪽), "개선 제품명/설명"(12쪽), "제품/서비스 이미지"(2쪽),
   "시장정의/목표고객"(2쪽) — 전부 보고서 생성 화면에서 그때그때 입력받고 DB 에는 저장하지
   않는다.** 이 네 항목은 워크시트 데이터가 아니라 보고서 한 번 쓸 때의 서술문·사진이라
   재사용 빈도가 낮고, `Project` 에 필드를 추가하면 이번 기능이 또 마이그레이션을 요구하게
   된다(이번 세션에서 이미 PR #32 로 `npx prisma migrate deploy` 를 하나 요청해 둔 상태다
   — 또 하나 얹지 않는다). 재생성할 때마다 다시 입력해야 하는 비용은 감수한다.
4. **KS-QFD 개선 방향성(12쪽)은 WS-13 을 그대로 읽어 채운다 — 자유입력이 아니다.**
   초안에서는 WS-13 이 "분기별 로드맵"이라 이 절과 안 맞는다고 적었는데, 화면 코드
   (`components/project/TechRoadmapTable.tsx`)를 직접 확인해 보니 틀렸다. WS-13 화면
   제목이 `[WS-13] KS-QFD를 활용한 제품/서비스의 개선 방향성` 이고 열도
   `개선 방향(차별화) / 개선기능 및 성능향상 / 구현가능성 / 목표 고객` 으로 이 절과
   똑같다. Prisma 필드명(`category`/`techItem`/`currentLevel`/`targetLevel`)만 옛
   로드맵 시절 잔재로 남아 있을 뿐이라, 필드명이 아니라 **화면이 부여한 의미**를 기준으로
   매핑한다. 즉 이 절은 GAP 이 아니라 DB 다.
5. **자금 비교 꺾은선그래프(13쪽)는 이번 범위에서 뺀다.** `FundingPlan` 표만 넣는다.
   신규 차트 컴포넌트 하나가 늘어나는 비용 대비, 표에 이미 같은 숫자(매출액·소요자금
   합계)가 있어 문서 안에서 정보 손실은 없다. 필요해지면 별도 계획으로 추가한다.
6. **"코치명"(1쪽 표지)** — 기존 `GET /api/projects/[id]/mentors` 를 그대로 호출해 채운다.
   코드를 확인해 보니 배정은 `ProjectMember.role = 'COACH'` 로 기록된다(`'MENTOR'` 가
   아니다 — 초안에서 잘못 적었던 것을 바로잡는다). 이건 서술문이 아니라 실제 구조화
   데이터라 3번과 다르게 DB 조회로 채우며, 새 필드가 아니라 기존 조회 하나를 더 하는
   것이라 마이그레이션이 필요 없다.
   **단, 이 엔드포인트는 `canAssignMentor()`(ADMIN·PROGRAM_MANAGER 만) 게이트가 걸려
   있어 MENTEE 가 호출하면 403 이다.** 그러므로 보고서 화면은 403 을 오류로 띄우지 말고
   **조용히 빈칸 처리**한다 — 코치명 하나 때문에 멘티가 보고서를 못 뽑으면 안 된다.
