# 12부. 문제 해결과 운영 지침

화면에 뜬 문구를 기준으로 원인을 찾는 부다. 문구를 그대로 검색해 해당 절로 가면 된다.

## 12.1 로그인·가입 오류 사례집

### 초대 코드 로그인이 거절된다

> 이메일과 초대 코드를 확인하세요. 이용 기한이 만료되었거나 사용할 수 없는 코드입니다.

이 문구는 **거절 사유를 구분하지 않는 공통 응답이다.** 기한이 지나지 않았어도 나온다.
다음 중 하나에 해당한다.

| 실제 원인 | 확인 방법 | 조치 |
| --- | --- | --- |
| 코드를 잘못 입력했다 | 메일의 코드와 대조한다. 대소문자와 하이픈 차이는 무시된다 | 다시 입력한다 |
| 초대받은 주소가 아닌 다른 이메일로 시도했다 | 초대 관리 화면에서 그 코드의 등록 이메일을 본다 | 등록된 주소로 로그인한다 |
| 초대 코드의 이용 기한이 지났다 | 초대 관리 화면의 기한 날짜를 본다 | 기한을 연장한다 |
| 프로그램이 종료됐다 | 프로그램 관리 화면의 종료일을 본다 | 프로그램 종료일을 늦추거나 새 프로그램으로 옮긴다 |
| **그 이메일로 이미 가입된 계정이 있다** | 회원 관리 목록에서 이메일을 검색한다 | 아래 별도 절차를 따른다 |

마지막 경우가 실제로 가장 흔하고 가장 헷갈린다. 멘티가 초대 메일을 보기 전에
회원가입 화면에서 직접 가입했다가, 뒤늦게 메일 안내대로 초대 코드 로그인을 시도할 때
생긴다. 코드는 멀쩡한데 "기한 만료"라고 보이므로 기한만 계속 늘려도 풀리지 않는다.

초대 코드 로그인은 아직 쓰지 않은 코드를 처리할 때 그 이메일로 이미 회원이 있으면
연결을 거부한다. 남의 이메일로 먼저 가입해 두고 정당한 초대를 가로채는 일을 막기
위한 정책이다. 그래서 **회원 쪽을 정리해야 풀린다.**

**해결 절차 A — 기존 계정을 살려서 초대에 연결한다(권장).**

1. 회원 관리에서 그 계정을 찾아 **승인**한다. 직접 가입한 계정은 승인 대기 상태다.
2. 프로그램 관리의 멘티 배정에서 **초대와 같은 프로그램**에 배정한다. 배정 후보에는
   승인된 멘티만 나오므로 1 번을 먼저 해야 한다.
3. 초대 관리에서 그 초대의 **이용 기한 날짜를 저장**한다. 저장할 때 조건이 맞는 기존
   멘티를 초대에 연결하고 계정의 이용 기한까지 함께 기록한다.
4. 멘티가 다시 초대 코드로 로그인한다.

3 번은 **현재 기한보다 늦은 날짜만** 저장할 수 있다. 초대 기한이 이미 프로그램
종료일과 같아 더 늦출 수 없으면 이 방법으로는 연결되지 않는다. 그때는 2 번까지만
하고 멘티에게 "비밀번호 로그인"을 쓰게 한다. 다만 이 경우 계정에 이용 기한이 남지
않으므로, 기한 관리가 필요하면 회원 관리의 기간 연장으로 따로 지정한다.

**해결 절차 B — 잘못 만든 계정을 지우고 초대를 다시 발급한다.**

계정을 삭제하면 **그 이메일로 발급된 초대 코드도 함께 지워진다.** 멘티가 메일로 받은
코드는 무효가 되므로 새 초대를 발급하고 다시 안내해야 한다. 절차와 주의사항은
[12.4](#124-멘티-계정-삭제-운영-지침)에 있다.

> 참고. 이미 가입한 멘티가 회원가입 화면에서 초대 코드를 넣어 다시 가입해도 풀리지
> 않는다. 가입 API 는 코드를 보기 전에 "이미 사용 중인 이메일입니다." 로 먼저 막는다.

### 비밀번호 로그인이 거절된다

| 문구 | 상태 | 원인과 조치 |
| --- | --- | --- |
| 이메일 또는 비밀번호가 올바르지 않습니다. | 401 | 계정이 없거나 비밀번호가 틀렸다. 어느 쪽인지 구분해 알려 주지 않는 것이 정상이다 |
| 선택한 로그인 역할과 계정 역할이 일치하지 않습니다. 계정에 맞는 역할을 선택하세요. | 403 | 로그인 화면 위쪽의 역할 버튼을 계정 역할에 맞게 다시 고른다 |
| 계정 역할 정보가 올바르지 않습니다. 관리자에게 문의하세요. | 403 | 계정의 역할 값이 알 수 없는 값이다. 관리자가 회원 관리에서 역할을 다시 지정한다 |
| 관리자 승인 대기 중인 계정입니다. 승인 후 로그인할 수 있습니다. | 403 | 관리자가 회원 관리에서 승인한다 |
| 이용 기간이 만료되었습니다. 관리자에게 연장을 요청하세요. | 403 | 회원 관리의 기간 연장 또는 초대 관리의 기한 변경으로 연장한다 |
| 로그인 시도가 너무 많습니다. N초 후 다시 시도하세요. | 429 | 안내된 시간만큼 기다린다. 제한은 접속 IP 와 이메일 조합으로 걸린다 |

역할 불일치 문구는 **실제 계정 역할을 알려 주지 않는다.** 계정 역할을 캐내는 통로가
되지 않도록 일부러 고정 문구로 둔 것이므로, 사용자가 역할을 모르면 관리자가 회원
관리 목록에서 확인해 알려 준다.

### Google 로그인이 거절된다

로그인 화면 주소 끝에 `?error=` 로 붙는 값에 따라 아래 문구가 뜬다.

| 코드 | 화면 문구 | 조치 |
| --- | --- | --- |
| `google_unconfigured` | Google 로그인이 아직 설정되지 않았습니다. 관리자에게 문의하세요. | 서비스 설정에서 Google OAuth 를 설정한다 |
| `google_denied` | Google 로그인을 취소했습니다. | 다시 시도한다 |
| `google_state` | 로그인 시도가 만료되었습니다. 다시 시도하세요. | 로그인 화면부터 다시 시작한다 |
| `google_unverified` | 확인되지 않은 Google 이메일입니다. | Google 계정에서 이메일 인증을 마친다 |
| `no_account` | 이 Google 계정으로 가입된 회원이 없습니다. 먼저 회원가입을 해주세요. | 같은 주소로 가입하거나 관리자가 계정을 만든다 |
| `pending` | 가입 승인 대기 중입니다. 관리자 승인 후 이용할 수 있습니다. | 관리자가 승인한다 |
| `expired` | 이용 기간이 만료되었습니다. 관리자에게 연장을 요청하세요. | 기간을 연장한다 |
| `google_failed` | Google 로그인에 실패했습니다. 다시 시도하세요. | 다시 시도하고, 반복되면 설정을 점검한다 |
| `google_role` | 로그인 역할을 다시 선택해 주세요. | 역할 버튼을 고른 뒤 Google 버튼을 누른다 |
| `role_mismatch` | 선택한 로그인 역할과 계정 역할이 일치하지 않습니다. 계정에 맞는 역할을 선택하세요. | 계정 역할에 맞는 버튼을 고른다 |
| `account_role_invalid` | 계정 역할 정보가 올바르지 않습니다. 관리자에게 문의하세요. | 관리자가 역할을 다시 지정한다 |

`google_state` 와 `google_role` 은 역할 정보가 담긴 서명값이 없거나 변조됐을 때
나온다. 로그인 화면을 거치지 않고 Google 주소를 직접 열면 재현되므로, 항상 로그인
화면의 버튼으로 시작하도록 안내한다.

### 로그인은 되는데 화면이 열리지 않는다

| 증상 | 원인 | 조치 |
| --- | --- | --- |
| 온보딩 화면에서 더 나아가지 못한다 | 임시 비밀번호를 아직 바꾸지 않았거나 프로필 필수 항목이 비었다 | 화면의 단계를 끝까지 마친다 |
| 관리자 화면만 "이 계정에는 관리자 권한이 없습니다" 가 뜬다 | 역할·권한 문제가 아니라 온보딩 관문에 걸린 것일 수 있다 | [12.3](#123-관리자-계정비밀번호-복구)을 따른다 |
| 대시보드가 비어 있다 | 프로젝트가 아직 없거나 배정되지 않았다 | 프로그램 배정과 프로젝트 소유자를 확인한다 |

## 12.2 메일이 오지 않을 때

초대 코드와 설문 초대는 모두 서비스 설정에 저장된 SMTP 로 나간다. 메일 발송은
**조용히 성공으로 처리하지 않는다.** 실패하면 화면에 다음이 뜬다.

> 메일 발송에 실패했습니다. SMTP 설정을 확인하고 다시 시도하세요.

점검 순서는 이렇다.

1. **서비스 설정에서 SMTP 가 설정돼 있는지 확인한다.** 설정이 비어 있으면 서버는
   메일을 보내지 않고 실패로 응답한다. 자세한 항목은 [3.8](03-admin.md)에 있다.
2. **포트와 보안 설정을 확인한다.** 465 포트는 보안 연결로 처리되고 그 밖의 포트는
   일반 연결로 처리된다. 메일 서비스가 요구하는 포트와 맞춰야 한다.
3. **계정과 앱 비밀번호를 확인한다.** 2 단계 인증을 쓰는 계정은 일반 비밀번호가 아니라
   앱 전용 비밀번호를 넣어야 한다.
4. **수신함의 스팸함을 확인하게 한다.** 발송은 성공했는데 도착하지 않는 대부분의
   경우다.
5. **그래도 오지 않으면 코드를 직접 전달한다.** 초대 관리 목록에서 코드를 확인해
   다른 경로로 알려 주고, 멘티는 그 코드로 로그인하면 된다. 메일 재발송은 이용 기한을
   늘리지 않는다.

발송 실패 로그에는 **수신자 주소와 코드가 남지 않는다.** 오류 코드만 남으므로 로그를
뒤져 누구에게 실패했는지 찾을 수는 없다. 대상은 화면의 목록에서 확인한다.

## 12.3 관리자 계정·비밀번호 복구

관리자 화면에 들어갈 수 없을 때의 절차다. 명령은 **실데이터가 있는 원격 DB 를 바라보는
운영자 터미널에서 사람이 직접 실행한다.**

### 관리자 화면이 열리는 조건

관리자 모드는 별도 계정이 아니라 일반 계정에 붙는 권한이다. 로그인 관문과 관리자
관문을 모두 통과해야 열린다.

| 값 | 검사 지점 | 통과 조건 |
| --- | --- | --- |
| `status` | 로그인 | `APPROVED` 여야 한다 |
| `accessExpiresAt` | 로그인 | 비어 있거나 미래여야 한다 |
| `mustChangePassword` | 온보딩 관문 | `false` 여야 한다 |
| 회원 프로필 | 온보딩 관문 | 역할에 필요한 항목을 갖춰야 한다 |
| `role` | 관리자 관문 | `ADMIN` 이어야 한다 |
| `isAdmin` | 관리자 관문 | `true` 면 통과한다 |
| `ADMIN_EMAILS` | 관리자 관문 | `role=ADMIN` 인 계정의 주소가 목록에 있으면 통과한다 |

**온보딩 관문에 걸리면 화면에는 "이 계정에는 관리자 권한이 없습니다" 로 보인다.**
원인과 전혀 다른 문구라서 권한 값만 들여다보면 찾지 못한다. 관리자 화면에서 만든
계정은 임시 비밀번호 상태로 시작하므로 이 경우가 실제로 생긴다.

### 1단계 — 누가 관리자인지 찾는다

```sh
npm run find:admin
```

DB 를 읽기만 하므로 먼저 돌려도 안전하다. 결과를 읽는 법은 이렇다.

- `[들어갈 수 있음]` 이 있다. 계정은 살아 있고 비밀번호만 잃은 것이므로 2단계로 간다.
- `[막힘]` 만 있다. 붙어 있는 이유가 원인이며 2단계가 상태·권한을 한꺼번에 바로잡는다.
- `[막힘]` 의 이유가 **온보딩 관문**이다. 2단계로 풀리지 않는다. 그 계정의 주인이 직접
  로그인해 비밀번호 변경과 프로필 작성을 마쳐야 열린다.
- 아무 계정도 없다. 관리자가 실제로 없으므로 2단계에서 만든다.
- `ADMIN_EMAILS 에 있으나 계정이 없는 주소` 가 보인다. 환경 변수만 채워져 있고 계정이
  없는 상태다. 2단계에서 계정을 만든다.

### 2단계 — 권한을 바로잡고 임시 비밀번호를 받는다

```sh
npm run seed:admin -- <이메일> --reset-password
```

대상 DB 와 계정을 보여 주고 확인을 받은 뒤에만 쓴다. 계정이 있으면 승인·관리자
플래그·역할을 맞추고, 없으면 새로 만들며 기본 프로필까지 넣는다. `--reset-password`
를 주면 임시 비밀번호를 새로 발급하고 기존 로그인 세션을 전부 끊는다.

임시 비밀번호는 **터미널에 한 번만 표시되고 어디에도 저장되지 않는다.** 창을 닫기 전에
옮겨 적는다. 잃으면 같은 명령을 다시 돌린다. 권한만 바로잡으려면 `--reset-password`
를 뺀다.

### 3단계 — 로그인하고 비밀번호를 바꾼다

`/admin` 에서 그 이메일과 임시 비밀번호로 로그인한 뒤 곧바로 비밀번호를 바꾼다.
이때도 다른 기기의 세션은 끊어진다.

### 주의

- 임시 비밀번호를 메신저·이슈·커밋 메시지에 남기지 않는다.
- `ALLOW_DEV_ADMIN` 은 로컬 개발용 우회이며 배포 환경에서는 동작하지 않는다. 복구
  수단으로 쓰지 않는다.
- 관리자는 화면에서 임명되지 않는다. 첫 관리자와 잃어버린 관리자는 위 스크립트로만
  되살린다.

## 12.4 멘티 계정 삭제 운영 지침

**막는 것이 기본이고, 지우는 것은 개인정보를 파기해야 할 때만 한다.**

| 상황 | 조치 |
| --- | --- |
| 프로그램이 끝났다 | 승인 취소 |
| 이용 기간이 만료됐다 | 승인 취소 또는 그대로 둔다 |
| 중도 이탈했다 | 승인 취소 |
| 문제 행동으로 접근을 막아야 한다 | 승인 취소 |
| 본인이 계정 삭제·개인정보 파기를 요구했다 | 삭제 |
| 잘못 만든 계정이거나 테스트 계정이다 | 삭제 |

승인 취소는 상태를 되돌리고 세션을 끊는다. 로그인도, 이미 로그인해 둔 기기도 즉시
막힌다. 데이터는 한 줄도 건드리지 않으므로 **접근 차단이 목적이라면 삭제가 나은 점이
하나도 없다.**

### 삭제 절차

1. 회원 관리 목록에서 대상 행의 삭제를 누른다.
2. 확인창에서 한 번 더 삭제를 누른다. 이때는 아무것도 지워지지 않고 서버가 무슨 일이
   벌어질지 계산해 돌려준다.
3. 마지막 확인 창에서 결과를 읽는다. 어느 프로젝트가 누구에게 넘어가는지, 이력 몇 건의
   주인이 비워지는지, 초대 코드 몇 건이 지워지는지가 나온다.
4. 삭제 사유를 고른다. 고르기 전에는 확정 버튼이 눌리지 않는다.
5. 삭제를 누르면 실행된다. 되돌릴 수 없다.

읽고 나서 마음이 바뀌면 뒤로를 눌러 되돌아갈 수 있다. 되돌아간 뒤 다시 진행해도
마지막 확인을 다시 거친다.

| 사유 | 쓰는 때 |
| --- | --- |
| 본인 요청 | 정보주체가 계정 삭제나 개인정보 파기를 요구했다 |
| 오등록 | 잘못 만든 계정, 테스트 계정 |
| 보유기간 경과 | 보관 기간이 지나 정리한다 |

사유는 파기의 증빙이다. 로그에 사유와 건수가 남고 이메일은 남지 않는다.

### 무엇이 사라지고 무엇이 남는가

| 사라진다 | 남는다 |
| --- | --- |
| 이름·이메일·비밀번호 | 소유했던 프로젝트와 그 안의 워크시트 전부 |
| 소속·직책·연락처·기업 정보 | 설문 초대와 응답. 발송자만 비워진다 |
| 개인 AI 연결 설정과 저장된 키 | 엑셀 가져오기 이력. 가져온 사람만 비워진다 |
| 그 이메일로 발급된 초대 코드 전부 | 다른 사람이 만든 프로젝트의 내용 |
| 다른 프로젝트에 참여한 기록 | |

소유했던 프로젝트는 **그 프로그램의 매니저에게 넘어간다.** 프로그램은 멘티들의
프로젝트로 구성되므로 사람이 빠졌다고 작업물이 사라지면 안 된다.

설문 응답자의 이메일은 응답자의 정보이고 프로젝트에 속한다. 멘티를 지워도 건드리지
않는다.

### 알아 둘 것

- **재가입해도 이전 프로젝트는 돌아오지 않는다.** 같은 이메일로 다시 가입하면 새
  계정이다.
- **프로그램 담당자는 이 절차로 지울 수 없다.** "담당 중인 프로그램이 있어 삭제할 수
  없습니다" 가 나오면 담당자를 다른 사람으로 먼저 옮긴다.
- **다른 역할의 삭제는 다르게 동작한다.** 멘토·매니저는 소유한 프로젝트가 함께
  삭제된다. 이 지침은 멘티 전용이다.

### 파기 완료를 답할 때

운영 DB 에서는 즉시 파기되지만 백업본은 그렇지 않다. 두 가지를 함께 말해야 정확하다.

- 운영 DB 에서 파기했다.
- 자동 백업본은 최대 7 일 뒤 소멸한다.

> 회원님의 계정과 개인정보를 운영 데이터베이스에서 파기했습니다. 자동 백업본에 남은
> 사본은 보존 주기에 따라 최대 7일 뒤 소멸합니다.

백업 정책이 바뀌면 이 숫자도 함께 고쳐야 한다. 7 일 안에 백업을 복원했다면 그 사이
파기한 계정이 되살아났는지 확인하고, 되살아났다면 같은 절차로 다시 지운다.

DB 덤프 파일에는 개인정보가 그대로 들어 있다. **쓰고 나면 즉시 지운다.**

## 12.5 프로그램·프로젝트 소유권 정리

프로그램과 프로젝트는 사람을 지우는 것만으로 사라지지 않도록 묶여 있다. 정리 순서를
지키지 않으면 삭제가 막힌다.

| 하려는 일 | 먼저 해야 할 일 |
| --- | --- |
| 프로그램 담당 매니저를 지운다 | 그 프로그램의 담당자를 다른 사람으로 옮긴다 |
| 프로그램을 지운다 | 그 프로그램의 프로젝트를 먼저 정리한다 |
| 멘티를 지운다 | 확인창의 이관 내역을 읽고 사유를 고른다. 프로젝트는 매니저에게 넘어간다 |
| 멘티를 다른 프로그램으로 옮긴다 | 프로그램 관리의 멘티 배정에서 옮긴다. 연결된 초대 코드의 프로그램도 함께 바뀐다 |

프로젝트 소유자를 바꿔야 할 때는 프로그램 관리의 소유권 이전 기능을 쓴다. 멘티 계정을
지워서 소유권을 옮기는 것은 개인정보 파기를 겸하므로, 소유권만 옮길 목적이라면 쓰지
않는다.

## 12.6 AI 기능이 동작하지 않을 때

AI 연결이 실패해도 **작업은 멈추지 않는다.** 규칙 기반으로 자동 전환되어 초안이 계속
만들어진다. 따라서 "AI 가 붙지 않는다"는 대개 결과 품질의 문제이지 오류가 아니다.

개인 API 키 연결 확인에서 나오는 안내는 벤더 원문을 그대로 보여 주지 않는다. 키 값과
벤더 응답 본문은 화면·로그·응답 어디에도 남지 않도록 고정 문구로 바꿔 표시한다.
Gemini 의 경우 키가 무효인지, 키에 제한이 걸렸는지, 이용 지역·결제 설정 문제인지를
구분해 안내한다. 자세한 내용과 벤더별 키 형식은 [10부](10-ai-features.md)에 있다.

## 12.7 운영 중 하지 말아야 할 것

- **운영 DB 에 직접 쓰는 작업을 임의로 하지 않는다.** 마이그레이션 적용과 스키마 변경은
  정해진 절차로만 한다.
- **임시 비밀번호·초대 코드·회원 이메일을 메신저나 이슈에 옮겨 적지 않는다.**
- **메일 재발송으로 기한이 늘어난다고 안내하지 않는다.** 재발송은 코드를 다시 보내는
  것일 뿐 기한을 바꾸지 않는다.
- **접근 차단 목적으로 계정을 삭제하지 않는다.** 승인 취소로 충분하다.
