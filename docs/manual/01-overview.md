# 1부. 솔루션 개요

## 1.1 KS-QFD 란

KS-QFD 는 제품·기술 기획을 17 장의 워크시트로 순서대로 풀어 가는 웹 솔루션이다.
자사 매출 추정에서 시작해 제품 속성과 고객 요구사항을 정리하고, Kano 설문으로
요구사항의 성격을 판정한 다음, QFD 로 고객 요구를 기술 특성에 옮기고, 기능기술
체계도와 목표 스펙을 거쳐 개발계획과 자금계획까지 이어진다. 마지막에는 각
워크시트의 결과와 멘토 분석을 모아 Word 결과보고서로 내보낸다.

멘티가 워크시트를 작성하고, 배정된 멘토가 검토 의견과 분석을 남기며, 프로그램
매니저와 관리자가 참여자와 프로그램을 운영하는 구조다.

## 1.2 워크시트 흐름

프로젝트를 열면 상단에 워크시트 메뉴가 붙는다. 맨 앞의 "프로젝트 개요"를 빼면
다음 16 개 화면이 순서대로 놓인다.

| 번호 | 워크시트 | 화면 주소 뒤 경로 |
| --- | --- | --- |
| WS-1 | 자사매출추정표 | `sales` |
| WS-2 | AS-IS 스펙표 | `spec` |
| WS-3 | 제품속성서 | `attributes` |
| WS-4 | 제품속성적합도 | `attributes/fitness` |
| WS-5 | 고객요구사항도출표 | `requirements` |
| WS-6 | Kano 질문지 | `kano` |
| WS-7 | Kano 분석 집계표 | `kano/analysis` |
| WS-9 | QFD | `qfd` |
| WS-10 | 기능기술체계도 | `tech-tree` |
| WS-11 | 개선포인트도출 | `improvements` |
| WS-12 | 최종목표스펙도출 | `target-spec` |
| WS-13 | 향후목표고객LIST | `tech-roadmap` |
| WS-14 | 개발계획서 | `dev-plan` |
| WS-15 | 핵심자산 및 보완자산 도출표 | `assets` |
| WS-16 | 자금소요계획표 | `funding-plan` |
| WS-17 | 자금조달계획표 | `funding-source` |

**WS-8 은 결번이다.** 화면 메뉴에 WS-8 항목이 없고 WS-7 다음이 바로 WS-9 QFD 다.
왜 비었는지는 화면과 코드 어디에도 적혀 있지 않다. 번호를 당겨 쓰지 말고 결번으로
두고 읽는다.

표의 두 워크시트는 주소와 실제 화면이 다르므로 주의한다.

- **WS-7 은 `kano/analysis` 주소에 표가 없다.** 그 주소는 "Kano 분석 결과가 WS-7로
  통합되었습니다" 안내와 이동 버튼만 있는 화면이다. 실제 집계표와 그래프는 프로젝트
  개요 화면의 "[WS-7] TIMKO/만족계수 그래프" 탭에 있다.
- **WS-4 는 주소로 연 화면과 개요 탭의 화면이 서로 다르다.** 주소로 열면 슬라이더로
  점수를 매기는 화면이고, 개요 탭에서는 시장·고객별 우선순위를 찍는 표 화면이다.
  저장되는 곳도 서로 다르다. 자세한 내용은 [7부](07-worksheets.md)에 있다.

워크시트는 앞에서 뒤로 값이 흐른다. 큰 줄기는 다음과 같다.

```
WS-2 AS-IS 스펙 ──┬──> WS-3 제품속성 ──> WS-4 적합도
                  │
                  └──> WS-10 기능기술체계도 ──> WS-9 QFD 기술특성
WS-5 고객요구사항 ──> WS-6 Kano 질문지 ──> 설문 응답 ──> WS-7 집계·그래프
                  │                                          │
                  └────────> WS-9 QFD 요구사항 행 <───────────┘
WS-9 ──> WS-11 개선포인트 ──> WS-12 최종목표스펙 ──> WS-14 개발계획
                                                  └──> WS-16·WS-17 자금계획
```

각 화면이 실제로 무엇을 불러오고 무엇을 넘기는지는 [7부](07-worksheets.md)에 적었다.

## 1.3 사용자 역할

시스템 역할은 네 가지이며, 여기에 계정이 없는 설문 응답자가 더해진다.

| 역할 | 내부 값 | 하는 일 |
| --- | --- | --- |
| 관리자 | `ADMIN` | 모든 권한. 회원 승인·삭제, 역할 전환, 프로그램 개설, 서비스 설정 |
| 프로그램 매니저 | `PROGRAM_MANAGER` | 담당 프로그램 운영. 초대 코드 발행, 멘토 배정, 프로젝트 개설. 멘토를 겸할 수 있다 |
| 멘토 | `MENTOR` | 배정된 멘티의 프로젝트만 열람·편집. 워크시트 의견과 분석 작성 |
| 멘티 | `MENTEE` | 자신의 프로젝트에서 워크시트를 작성한다 |
| 설문 응답자 | 없음 | 초대 링크로 Kano 설문에만 응답한다. 계정이 없다 |

역할별 권한은 다음과 같다. 근거는 `lib/member-roles.ts` 의 판정 함수다.

| 할 수 있는 일 | 관리자 | 매니저 | 멘토 | 멘티 |
| --- | --- | --- | --- | --- |
| 회원 계정 생성·승인·삭제 | O | X | X | X |
| 멘티 초대 코드 발행 | O | O | X | X |
| 프로그램 개설 | O | X | X | X |
| 프로그램 운영 화면 접근 | O | O | X | X |
| 프로젝트에 멘토 배정 | O | O | X | X |
| 프로젝트 개설 | O | O | 조건부 | O |
| 남을 소유자로 지정해 개설 | O | O | X | X |
| 전체 프로젝트 목록 열람 | O | O | X | X |
| 모든 프로젝트 내용 열람 | O | O | X | X |
| 모든 프로젝트 내용 편집 | O | X | X | X |

멘토의 프로젝트 개설은 관리자가 그 멘토에게 개별로 허용한 경우에만 열린다.
허용 전에는 대시보드의 개설 버튼이 "새 프로젝트 (사용중지)" 로 비활성 상태다.

**역할 전환은 매니저와 멘토 사이에서만 일어난다.** 관리자와 멘티는 역할 전환으로
드나들 수 없다. 멘티가 되는 길은 가입할 때 멘티를 고르거나, 멘티용 초대 코드를
받거나, 관리자가 멘티 계정을 직접 만드는 세 가지뿐이다.

프로젝트 안에서 쓰이는 역할(소유자·편집자 등)은 이 시스템 역할과 별개다. 시스템
역할은 "이 사람이 시스템에서 무엇을 할 수 있는가"를, 프로젝트 역할은 "이 프로젝트
안에서 무엇을 할 수 있는가"를 정한다. 프로젝트 역할은 [7부](07-worksheets.md)의
프로젝트 설정 절에 정리했다.

## 1.4 프로그램·프로젝트·참여자의 관계

```
프로그램 (담당 매니저 1명, 종료일 있음)
  ├─ 소속 멘티들
  │    └─ 멘티의 프로젝트 (소유자 = 멘티)
  │         ├─ 워크시트 WS-1 ~ WS-17
  │         ├─ 배정 멘토
  │         └─ 팀원
  └─ 멘티 초대 코드 (이메일 1개당 1장, 이용 기한 있음)
```

- **프로그램**은 관리자만 개설한다. 프로그램마다 담당 매니저와 종료일이 있다.
- **멘티는 프로그램 하나에 속한다.** 초대 코드로 들어오면 그 코드의 프로그램으로
  정해지고, 관리자가 나중에 다른 프로그램으로 옮길 수 있다.
- **멘토는 프로그램에 묶이지 않는다.** 여러 프로그램의 프로젝트에 배정될 수 있어서
  초대 코드로 모집하지 않고 정식 가입과 관리자 승인으로 들어온다.
- **프로젝트는 멘티가 소유한다.** 멘티는 직접 1 개를 열 수 있고, 그 이상은 승인을
  받아야 한다. 매니저와 관리자는 멘티를 소유자로 지정해 대신 열어 줄 수 있다.
- **프로그램 종료일은 모든 이용 기한의 상한이다.** 초대 코드의 기한을 아무리 늦게
  잡아도 프로그램이 끝나면 접근이 막힌다.

## 1.5 이용 기한의 구조

초대 코드로 들어온 계정에는 이용 기한이 있고, 관리자가 직접 만든 계정에는 없다.
기한은 세 값 중 가장 이른 시점에 끝난다.

1. 프로그램 종료 시각
2. 초대 코드에 지정된 이용 기한
3. 기한을 따로 지정하지 않은 코드라면 첫 로그인 시점부터 기본 90 일

기한이 지나면 로그인 자체가 막히고 "이용 기간이 만료되었습니다. 관리자에게 연장을
요청하세요." 가 뜬다. 연장은 관리자나 담당 매니저가 초대 관리 화면에서 날짜를
바꾸거나, 회원 관리 화면에서 기간을 연장해 처리한다.

## 1.6 화면 구조

로그인한 사용자의 기본 화면은 대시보드다. 역할에 따라 볼 수 있는 화면이 다르다.

| 화면 | 주소 | 접근 가능 역할 |
| --- | --- | --- |
| 소개 화면 | `/` | 비로그인 방문자 |
| 로그인 | `/login` | 전체 |
| 회원가입 | `/signup` | 전체 |
| 온보딩 | `/onboarding` | 첫 로그인 계정 |
| 대시보드 | `/dashboard` | 로그인 사용자 전체 |
| 사용자 정보 | `/profile` | 로그인 사용자 전체 |
| 프로젝트 개요 | `/project/{프로젝트ID}` | 소유자·팀원·배정 멘토·매니저·관리자 |
| 워크시트 | `/project/{프로젝트ID}/{워크시트경로}` | 위와 같음 |
| 결과보고서 | `/project/{프로젝트ID}/report` | 위와 같음 |
| 프로젝트 설정 | `/project/{프로젝트ID}/settings` | 소유자와 관리 권한자 |
| 엑셀 가져오기 | `/project/{프로젝트ID}/import` | 소유자와 관리 권한자 |
| 관리자 화면 | `/admin` | 관리자 |
| 매니저 화면 | `/manage` | 관리자·프로그램 매니저 |
| 서비스 설정 | `/settings` | 관리자 |
| 설문 응답 | `/survey/{토큰}` | 초대 링크를 받은 사람 |

관리자 화면과 매니저 화면을 나눈 이유가 있다. 관리자 화면에는 회원 삭제와 역할
변경이 있어 매니저에게 같은 화면을 열어 주고 탭만 숨기면 권한 경계가 화면 조건문에
기대게 된다. 그래서 매니저 전용 화면을 따로 두었다.
