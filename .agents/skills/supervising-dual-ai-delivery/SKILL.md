# Supervising Dual-AI Delivery

## Overview

감리 AI(수퍼바이저)가 계획·검증을, 실행 AI가 코딩을 맡는 이중화 체계의 운영 규율.

**핵심 원칙: 완료 보고서는 주장이다. 판정은 감리자의 독립 재현으로만 한다.**
보고서가 상세하고 정직해 보여도 판정 근거가 될 수 없다 — 판정 근거는 감리자가 직접
실행한 게이트, 직접 대조한 코드, 직접 조작한 화면뿐이다.

프로젝트별 값(게이트 명령, 환경 함정, 번호 관례, 브랜치 규칙)은 이 스킬에 없다 —
프로젝트 지침 파일(CLAUDE.md 등)에서 채운다. 없으면 먼저 만들어라.

## 위임 프롬프트 작성

**REQUIRED:** [prompt-template.md](prompt-template.md)의 절 구조를 그대로 사용한다.
절을 빼는 것은 허용, 순서 변경과 절 없이 흩어 쓰기는 비허용 — 빠진 절이 눈에 보여야 한다.

템플릿 밖에서 감리자가 프롬프트 발행 **전에** 끝내야 할 일:

1. **사전 조사로 좌표 확정** — 원인 파일:라인, 참조 구현 위치를 감리자가 직접 grep으로
   확인해 `[배경 — 검증된 사실]` 절에 주입한다. 실행 AI의 탐색·추측을 구조적으로 없앤다.
2. **공유 자원 예약** — 태스크 번호·시나리오 번호·migration 타임스탬프 등 충돌 가능한
   식별자는 감리자가 최대값을 확인해 프롬프트에 확정값으로 준다.
3. **결정권 경계 확정** — 이미 내린 결정은 `[확정된 계약]`에, 실행 중 바뀌면 안 되는
   전제는 `[Ask First — 중단 조건]`에 쓴다. 경계가 없으면 실행 AI는 재량과 일탈을
   구분할 수 없다. 지시와 기존 계약이 충돌할 때 "기존 계약을 따르고 이유를 보고하라"를
   기본 규칙으로 명시한다.
4. **완료 조건을 판정 가능하게** — 완료 판정의 모든 항목은 제3자가 참/거짓을 판정할 수
   있어야 한다. "가능하면", "적절히", "필요시" 가 완료 판정에 들어가면 그 항목은 없는
   것이다. 재량을 주려면 완료 판정이 아니라 작업 내용 절에 써라.

## 완료 보고 검증 — 판정 레시피

보고서 수령 후 판정은 다음 순서다. 각 단계의 산출이 다음 단계의 입력이다.

1. **경계 확인**: diff가 지시 범위에 국한되는지, 기존 테스트 약화(skip·삭제·단언 완화)나
   게이트 설정 변조가 없는지. 게이트 통과 확인보다 먼저 한다 — 변조된 게이트의 통과는
   무의미하다.
2. **표본 대조**: 보고서의 핵심 주장 3~5개를 골라 코드 파일:라인으로 직접 확인한다.
   표본은 "그 주장이 거짓이면 판정이 뒤집히는" 주장부터 고른다.
3. **회귀 테스트 역검증**: 새 회귀 테스트가 결함을 실제로 잡는지 — 수정만 임시로 되돌린
   상태에서 그 테스트가 실패하는지 확인 후 원복. 수정 전에도 통과하는 테스트는 회귀
   테스트가 아니다.
4. **게이트 직접 재실행**: 보고된 출력을 쓰지 않고 전체 게이트를 감리자가 실행한다.
5. **신설 실행물 1회 실행**: 이번 작업이 만든 스크립트·명령·엔드포인트는 병합 전에
   최소 1회 실제 실행한다. 테스트가 그린이어도 실행된 적 없는 코드에는 잠복 결함이
   남는다(spawn 옵션, CLI 플래그, 플랫폼 차이).
6. **화면 검증 3단계** — UI가 관련되면 반드시:
   - (a) **존재**: 요소·마크업이 렌더되는가
   - (b) **동작**: 클릭·입력·전이가 실제로 작동하는가 (임베드 프레임은 내용까지)
   - (c) **실사용자 도구**: 사용자가 쓸 그 도구(실제 브라우저)로 재현한다.
     curl·HTTP 클라이언트는 브라우저가 아니다 — 브라우저만 보내는 헤더·프로토콜
     차이로 통과/실패가 갈린다.
7. **배포 후 실환경 재검증**: 배포가 있는 작업이면 로컬 그린으로 끝내지 않는다.
   배포 플랫폼의 계약(번들러, 출력 요구, 런타임 제약)은 로컬에서 재현되지 않으므로,
   배포 직후 핵심 경로를 실환경에서 6번 기준으로 다시 밟는다.

판정: 하나라도 실패 → 파일:라인과 재현 방법을 담아 재작업 지시(감리자가 대신 고치지
않는다 — 단, 배포 직후 실환경에서만 드러난 소규모 결함은 감리자가 핫픽스하고 기록을
남기는 것을 허용한다). 전부 통과 → 승인·병합, 판정 근거를 기록.

## 합리화 금지 표

| 유혹 | 현실 |
|---|---|
| "보고서가 상세하고 정직하니 믿어도 된다" | 정직한 보고서도 자기가 못 본 결함은 못 쓴다. 판정 근거는 독립 재현뿐. |
| "게이트가 그린이니 화면은 안 봐도 된다" | 게이트는 게이트가 검사하는 것만 본다. 화면 결함은 화면에서만 보인다. |
| "curl로 확인했으니 브라우저도 될 것" | curl 통과·브라우저 실패는 실재하는 부류다(Origin/Sec-Fetch, HTTP 버전). |
| "로컬 전부 그린이니 배포도 될 것" | 배포 플랫폼 계약은 로컬에 없다. 배포에서만 죽는 결함이 있다. |
| "테스트를 추가했다니 회귀는 잡힐 것" | 수정 전에도 통과하는 테스트는 아무것도 잡지 않는다. 역검증하라. |
| "시간이 없으니 표본 검증만 하자" | 표본 검증은 게이트 재실행의 대체가 아니라 전 단계다. 순서를 줄이면 그 단계의 결함이 병합된다. |

## Red Flags — 멈추고 레시피로 돌아가라

- 보고서의 수치를 그대로 판정문에 옮겨 적고 있다
- "이미 에이전트가 테스트했으니까"로 게이트 재실행을 건너뛰려 한다
- UI 변경인데 검증 계획에 브라우저가 없다
- 병합 판정문을 쓰는데 신설 스크립트를 한 번도 실행하지 않았다
- 배포했는데 배포 URL을 한 번도 열지 않았다
