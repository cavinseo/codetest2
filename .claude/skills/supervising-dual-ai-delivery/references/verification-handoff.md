# 위임할 수 없는 검증을 사람에게 넘기기

환경 제약이 금지한 검증(실기동, 실DB 접속)은 실행 AI 에게 시키면 안 된다. 그렇다고
"확인 못 했다"로 끝내서도 안 된다. **누가 무엇을 어떻게 하는지 적어 넘긴다.**

---

## 지시서의 머리 — 수행 주체를 먼저 가른다

읽는 사람이 첫 화면에서 "내가 할 것"과 "AI 에게 시킬 것"을 구분할 수 있어야 한다.

```
| 구분 | 내용 | 수행 |
| --- | --- | --- |
| Part A | 실기동 검증 <N>건 | 감리자 또는 사용자 직접 |
| Part B | <DB 가 필요한 검증> | 감리자 직접 |
| Part C | 검증 전에 먼저 고칠 결함 <N>건 | 실행 AI 위임 가능 |
```

그리고 **왜 위임하지 않는지**를 규칙 원문으로 인용한다. 인용이 없으면 다음 사람이
"그냥 시키면 되지 않나" 하고 되돌린다.

---

## 검증 전에 고칠 것을 앞세운다

절차를 쓰다 보면 위임 때 못 본 결함이 나온다. 그것을 **Part C 로 앞세운다** —
고치지 않은 채 검증하면 결과가 왜곡되고, 검증자의 시간을 버린다.

이때 나온 결함은 코드 작업이므로 **위임 가능하다.** 그 자리에 위임 프롬프트를 함께
넣어 두면 지시서 하나로 흐름이 이어진다.

---

## 검증 항목 형식

각 항목을 **절차 → 통과 → 실패 시 적을 것** 순으로 쓴다.

```
#### V-<번호>. <한 줄 요약> (<어느 Task 를 검증하는가>)

1. <구체적 조작. 화면 이름과 버튼 이름을 실제 문구로>
2. <다음 조작>
3. <새로고침·재접속 등 상태를 다시 읽는 단계 — 있어야 화면 캐시에 속지 않는다>

- **통과:** <관찰 가능한 상태>
- **실패 A** — <증상> → <무엇을 뜻하는가>. <무엇을 알려줄지>
- **실패 B** — <다른 증상> → <무엇을 뜻하는가>
```

### 좋은 검증 항목의 조건

**조작이 구체적이다.** "속성을 수정한다"가 아니라 "속성명 끝에 `.` 하나를 추가한다".
검증자가 판단할 여지를 남기면 사람마다 다른 것을 검증한다.

**상태를 다시 읽는 단계가 있다.** 새로고침 없이 화면만 보면 "지웠다고 표시되는데 실제로
안 지워진" 결함을 못 잡는다.

**통과 조건이 둘 이상이면 둘 다 적는다.** "경고가 안 뜬다"와 "데이터가 남는다"는 다른
것이고, 하나만 만족하는 경우가 실제로 나온다.

**실패를 종류별로 나눈다.** 어느 실패인지에 따라 원인이 다르면 미리 갈라 둔다.
검증자가 "실패 B" 한 마디만 해도 감리는 원인을 안다.

---

## "부정" 검증을 넣어라

**무언가가 일어나지 않아야 하는** 항목이 대개 더 중요하다.

- 저장한 뒤에는 경고가 **뜨지 않아야** 한다
- 즉시 저장되는 화면에는 경고가 **붙지 않아야** 한다
- 안전한 편집에서는 확인창이 **뜨지 않아야** 한다

긍정 항목("경고가 뜬다")은 대충 만들어도 통과한다. 헛도는 경고를 잡는 것은 부정
항목뿐이고, 헛도는 경고는 한 번만 겪어도 사용자가 그다음부터 읽지 않는다.

---

## 대상이 둘로 갈리는 곳을 표로 못박는다

같은 이름의 화면이 두 경로에 있고 저장 대상이 다르면, 검증자가 엉뚱한 쪽을 보고
**거짓 통과**를 낸다. 이건 검증이 없는 것보다 나쁘다 — 확인했다고 믿게 되므로.

```
| 경로 | 저장 대상 | 이번 검증 대상인가 |
| --- | --- | --- |
| <경로 1> | <모델·형식> | 아니다 |
| <경로 2> | <모델·형식> | **그렇다** |
```

---

## 사전 준비를 빠뜨리지 않는다

- **검증용 데이터를 새로 만들게 한다.** 실사용 데이터로 검증하면 삭제 항목에서 진짜로
  잃는다
- 서버·컨테이너를 띄우는 명령을 복사-붙여넣기 가능한 형태로 준다
- 알려진 함정(포트 충돌, 파일 잠금 등)과 그때의 조치를 미리 적는다

---

## 보고 형식은 최대한 가볍게

통과는 한 글자로 끝나야 한다. 무겁게 만들면 검증이 안 돌아온다.

```
V-1 <요약>   [ ]
V-2 <요약>   [ ]   ← 핵심
...
```

**실패했을 때만** 자세히 받는다. 무엇을 받아야 원인을 좁힐 수 있는지 미리 적는다.

```
1. 어느 항목의 몇 번 절차에서
2. 무엇이 보였는가 (문구는 그대로, 화면은 캡처)
3. 환경 (브라우저·버전·URL 등)
```

---

## 판정 기준을 미리 적는다

결과를 받고 나서 정하면 늦다. **어떤 실패가 어떤 결정을 부르는지** 미리 적어 둔다.

```
| 결과 | 판정 |
| --- | --- |
| <가장 나쁜 실패> | 즉시 중단. <되돌릴 것>부터 |
| <회귀성 실패> | <어느 Task>가 무의미해진다. 재작업 |
| <범위 오류> | <무엇을>다시 센다 |
| 전부 통과 | <다음 단계 — 병합·PR 등> |
```
